## 1. מה עושה localSIEM

באמצעות **מודולים**, מודול אחד לכל שירות, localSIEM עוקב אחר השירותים של השרת שעליו הוא מותקן. הוא קורא רק את הלוגים של השרת הזה: הוא אינו מקבל לוגים ממחשבים אחרים. המודול **Apache + ModSecurity** עוקב אחר אתר האינטרנט של Apache: עבור כל בקשה הוא מצרף שלוש רשומות, השורה של `access.log`, השורות של `error.log` והרשומה של לוג הביקורת של ModSecurity, לפי ה-`UNIQUE_ID` של הבקשה. הכול נשמר לצורך חיפוש. לאחר מכן localSIEM מחליט מה צריך להישלח ל-SOC.

על אותו שרת Debian או Alpine שעליו הוא מגן, לצד אתר האינטרנט שלו, localSIEM פועל כשני שירותים של משתמש המערכת `localsiem`. ממשק האינטרנט שלו מאזין בפורט 10443: הוא לעולם אינו משתמש בפורטים 80 או 443 ולעולם אינו נוגע באתר האינטרנט של השרת. מלבד ה-SOC (אופציונלי, סעיף 5), הוא יכול לשלוח את ההתראות החשובות ביותר דרך **Telegram** (סעיף 14), והוא מעניק לאנליסט של ה-SOC **כלי חיפוש**: שדה חיפוש אחד וטווח זמן (סעיף 9). הוא לעולם אינו מוציא מהשרת סיסמאות, קובצי cookie, טוקנים או גופי בקשות, הוא צורך מעט זיכרון (כ-100 MB בשימוש רגיל, כ-200 MB בשיא) והוא לעולם אינו ממלא את הדיסק (סעיף 16).

**רק מה שאיש עדיין לא טיפל בו נשלח ל-SOC.**

| מצב | נשלח ל-SOC? |
|---|---|
| ModSecurity חסם את הבקשה בשלבים 1–2 (לפני שהאפליקציה קיבלה אותה) | **לא.** היא נשארת ב-localSIEM, זמינה לחיפוש, ומופיעה כספירה בהתראה הבאה של אותה IP. |
| ModSecurity חסם את התגובה בשלבים 3–4 (האפליקציה כבר הריצה את הבקשה) | כן |
| התאמות לכללים כש-ModSecurity במצב `DetectionOnly` (שום דבר אינו נחסם) | כן |
| התאמות לכללים מתחת לסף החסימה | כן, בחומרה `low` |
| אותות של הכללים של localSIEM (כוח גס, web shell, קובץ רגיש, מנייה, שגיאת מסד נתונים) | כן |
| בעיות תקינות ומחיקה אפשרית של עקבות | כן |

**החומרה של מה שנשלח ל-SOC**

| מצב | חומרה |
|---|---|
| התאמות לכללים שלא נחסמו, תשובה 3xx, 4xx או 5xx | בינונית |
| התאמות לכללים שלא נחסמו, תשובה 2xx | גבוהה |
| נחסמה בשלבים 3–4 | גבוהה |
| סימני הצלחה: כלל של דליפת נתונים או של web shell (950–955) שלא נחסם, שגיאת SQL מיד אחר כך, POST עם 2xx לקובץ `.php` חדש | קריטית |
| מתחת לסף החסימה (לרוב תוצאות חיוביות שגויות של האפליקציה) | נמוכה (ניתנת לשינוי בהגדרות) |

**קיבוץ.** התראה אחת לכל מודול, vhost, IP, קטגוריה וחומרה בחלון של 10 דקות. התראה קריטית יוצאת מיד; האחרות ממתינות 60 שניות כדי לאסוף את פרץ האירועים ויוצאות עם הספירה. סורק ששולח אלפי בקשות מפיק התראות ספורות, לא אלפים. אם החומרה עולה (לדוגמה, אותה מתקפה מקבלת עכשיו תשובות 200), זו התראה אחרת.

**מה שלעולם אינו נשלח ל-SOC:** גופי בקשות או תגובות, קובצי cookie, כותרות `Authorization`, סיסמאות או טוקנים — אפילו לא ממוסכים — ומה שכבר נחסם בשלבים 1–2 (רק כספירה). לפני שהוא שומר משהו, localSIEM ממסך את הערכים הרגישים (`password`, `pass`, `pwd`, `passwd`, `token`, `secret`, `api_key`, `apikey`, `auth`, `session` והכותרות `Authorization`, `Cookie`, `Set-Cookie`, `X-Api-Key`, `Proxy-Authorization`) עם `***`.

**מודולים.** הליבה של localSIEM (אחסון, חיפוש, כללים, קיבוץ, מסירה ל-SOC, תקינות) זהה לכל השירותים; כל מודול מוסיף את מה שייחודי לשירות אחד. המודול Apache + ModSecurity (`apache2`) מגיע מהמאגר `localSIEM-modules` (GitHub), והוא מותקן, מתעדכן ומוסר רק מממשק האינטרנט, לעולם לא על ידי תוכנית ההתקנה של localSIEM; התקנתו לעולם אינה מתקינה את Apache או את ModSecurity. כל המודולים מותקנים, מתעדכנים ומוסרים באותו אופן, מממשק האינטרנט. סעיף 13 מסביר איך להתקין ולעדכן אותם, לראות את מצבם, להפעיל ולכבות אותם ולהגדיר אותם.

## 2. התקנה

להתקנה יש שני שלבים: הליבה של localSIEM, ולאחר מכן המודולים שלו (שלב 2 בהמשך). יש להריץ בתור root, ישירות מ-GitHub:

```bash
# Debian 13
curl -fsSL -H 'Accept: application/vnd.github.raw+json' https://api.github.com/repos/PYMEHackers/localSIEM/contents/deploy/install-update-reinstall-debian.sh | bash -s -- --install --allow-from 203.0.113.10 --soc-token TOKEN
# Alpine 3.24 (תחילה: apk add bash curl)
curl -fsSL -H 'Accept: application/vnd.github.raw+json' https://api.github.com/repos/PYMEHackers/localSIEM/contents/deploy/install-update-reinstall-alpine.sh | bash -s -- --install --allow-from 203.0.113.10 --soc-token TOKEN
```

ממשק האינטרנט של localSIEM מאזין תמיד ב**פורט 10443 עם HTTPS**: תוכנית ההתקנה בודקת שהפורט פנוי ונעצרת אם שירות אחר משתמש בו. הפעולה והאפשרויות נכתבות אחרי `bash -s --`. תוכנית ההתקנה בודקת את מה שהיא צריכה (Python 3.13 עם `venv`, OpenSSL, תעודות ה-CA, כלי ה-ACL, logrotate, curl, tar) ומתקינה את מה שחסר. כשהיא מורצת כך, דרך צינור (pipe), היא מורידה את הענף `main` של `https://github.com/PYMEHackers/localSIEM`; כשהיא מורצת מעותק של הפרויקט (`bash deploy/install-update-reinstall-debian.sh --install`), היא מתקינה את העותק הזה.

**הפעולה.** תוכנית ההתקנה צריכה תמיד פעולה אחת; בלעדיה היא נעצרת ומציגה את רשימת הפעולות:

| פעולה | שימוש |
|---|---|
| `--install` | מתקינה את localSIEM בשרת שאין בו אותו. אם היא מוצאת משהו של localSIEM (`/opt/localsiem`, השירותים שלו או המשתמש `localsiem` שלו, גם מהתקנה שנכשלה באמצע), היא נעצרת ומפנה אל `--update` ואל `--reinstall`. |
| `--update` | מעדכנת את localSIEM המותקן: נשמרים הנתונים, החשבונות, ההגדרות, המודולים והאפשרויות שניתנו קודם (בהמשך). |
| `--reinstall [--yes]` | מוחקת את localSIEM המותקן עם כל הנתונים שלו, כפי ש-`--uninstall` עושה (בהמשך), ומתקינה אותו מחדש מאפס, עם סיסמאות חדשות. קודם לכן היא מבקשת להקליד `yes` (עם `--yes` היא אינה מבקשת; הדבר נדרש כשאין מסוף) ואינה מוחקת דבר עד שהעותק החדש הורד והאפשרויות נבדקו. האפשרויות של ההתקנה הקודמת אינן נשמרות: יש לציין אותן שוב. |
| `--uninstall [--yes]` | מוחקת מהשרת את localSIEM ואת כל הנתונים שלו (בהמשך). היא באה לבדה, בלי אפשרויות אחרות. |

הפעולות `--update` ו-`--reinstall` נעצרות כש-localSIEM אינו מותקן: יש להשתמש ב-`--install`.

האפשרויות של `--install`, `--update` ו-`--reinstall`:

| אפשרות | שימוש |
|---|---|
| `--allow-from LIST` | כתובות IP ו-CIDR המורשים לפתוח את ממשק האינטרנט, מופרדים בפסיקים: ה-SOC ומנהלי המערכת שלך |
| `--soc-url URL` | ברירת המחדל: `https://soc.pymehackers.com` |
| `--soc-token TOKEN` | טוקן הקליטה של לקוח זה ב-SOC. אופציונלי: בלי SOC, localSIEM פועל בכוחות עצמו (סעיף 5) |
| `--soc-ca-file PATH` | רק עבור SOC עם תעודה פרטית (שרתי בדיקות) |
| `--domain NAME` | שם השרת, עבור התעודה ועבור כתובת ה-SIEM (ברירת המחדל: שם המארח שלו) |
| `--certificate PATH --private-key PATH` | התעודה שבה יש להשתמש. בלעדיהן localSIEM מעתיק את תעודת Let's Encrypt של `--domain` אם יש כזו (ומעתיק אותה שוב בכל חידוש), או יוצר תעודה בחתימה עצמית. |
| `--retention-days N`, `--max-disk SIZE` | שמירת נתונים (סעיף 16) |
| `--enable-mfa`, `--disable-mfa` | אימות דו-שלבי מופעל (חובה לכל החשבונות) או כבוי. בלעדיהן, בהתקנה חדשה הוא כבוי, ועדכון שומר על מה שנבחר תחת ניהול › הגדרות (סעיף 14). |
| `--rotate-credentials` | יוצרת סוד חתימה חדש ל-JWT וכותבת אותו ב-`/root/webapp-credentials.txt` |
| `--ref REF` | הענף או התג של localSIEM להורדה (ברירת המחדל `main`) |
| `--source-url URL` | ארכיון (`.tar.gz`) של localSIEM להתקנה במקום זה של GitHub (אתר מראה) |
| `--modules-repository URL`, `--modules-ref REF` | המאגר (או ארכיון `.tar.gz`) והענף או התג שמהם ממשק האינטרנט מתקין ומעדכן מודולים (סעיף 13). ברירת המחדל: `https://github.com/PYMEHackers/localSIEM-modules`, הענף `main`. |

**תמיד הגרסה האחרונה.** GitHub שומר את הקבצים של `raw.githubusercontent.com` במטמון עד 5 דקות אחרי כל שינוי, ולכן הפקודות שלמעלה קוראות את תוכנית ההתקנה דרך ה-API של GitHub, שאין לו מטמון; לאחר מכן תוכנית ההתקנה שואלת את אותו API לאיזה commit מצביע הענף ומורידה בדיוק את ה-commit הזה, והיא מבקשת מכל שרת בדרך לא לענות בעותק מהמטמון. ללא טוקן, GitHub מתיר 60 בקשות API לשעה מכל כתובת IP: אם הוא מסרב, הפקודה נכשלת עם `403` (יש להמתין ולהריץ אותה שוב); אם רק השאלה של תוכנית ההתקנה נכשלת, תוכנית ההתקנה מזהירה ומורידה את הענף.

האפשרויות נשמרות ב-`/opt/localsiem/config/install.env`: הפעולה `--update` בלי אפשרויות שומרת עליהן. לעדכון:

```bash
# Debian 13 (Alpine: install-update-reinstall-alpine.sh)
curl -fsSL -H 'Accept: application/vnd.github.raw+json' https://api.github.com/repos/PYMEHackers/localSIEM/contents/deploy/install-update-reinstall-debian.sh | bash -s -- --update
```

הלוג של תוכנית ההתקנה הוא `/root/webapp-install.log`, והסיסמאות שהיא יוצרת נמצאות ב-`/root/webapp-credentials.txt` (שניהם בהרשאות 600). היא מציגה את ההתקדמות שלה בשלבים ממוספרים (`[3/12] Getting localSIEM`), עם `✓` למה שהושלם, `!` לאזהרות, `✗` לכשלים ו-`·` למידע, בצבע כשמדובר במסוף (`NO_COLOR=1` או `LOCALSIEM_COLOR=never` מכבים את הצבעים). הפלט של apt-get או apk, curl, tar ו-pip נכתב רק ללוג; כשאחד מהם נכשל, המסך מציג את 20 השורות האחרונות שלו. הלוג מקבל את אותן שורות, בלי צבעים, עם הזמנים בפורמט האחסון. בסיום היא מריצה את האבחון של כל מודול מופעל (סעיף 4) ומציגה סיכום: הכתובת של ממשק האינטרנט, שהיא גם כתובת ה-SIEM שיש למסור ל-SOC, קובץ האישורים, הלוג ומצב ה-SOC, ואחריהם הצעדים הבאים. אם היא נכשלת, היא מציינת באיזה שלב היא נעצרה.

**הסרת התקנה.** הפעולה `--uninstall` מוחקת את localSIEM מהשרת: היא עוצרת ומסירה את השירותים שלו ומוחקת את `/opt/localsiem` (קוד, הגדרות, מסד הנתונים עם כל האירועים וההתראות, תעודות ומודולים), את המשתמש `localsiem`, את הרשאת הקריאה ללוגים ש-`setup-modules` העניק, את התצורה של Apache (`localsiem.conf`) שהוסיפה האפשרות `--configure-apache` של גרסאות ישנות של מודול Apache (1.2.0 או מוקדמות יותר), עם configtest וטעינה מחדש של Apache, את הקובץ של logrotate, את ה-hook של Let's Encrypt ואת הרשומות של localSIEM ב-`/root/webapp-credentials.txt` (הקובץ נמחק כשלא נשאר בו דבר אחר). קודם לכן היא מבקשת להקליד `yes` (עם `--yes` היא אינה מבקשת; הדבר נדרש כשאין מסוף). אם לא נמצא בשרת דבר מ-localSIEM, היא מציגה «Nothing of localSIEM was found on this server.». הלוג של תוכנית ההתקנה, החבילות שתוכנית ההתקנה הוסיפה, `mod_unique_id` (Debian) והלוגים של Apache נשארים, וכך גם `localsiem_access.log` שהקובץ ההוא גרם ל-Apache לכתוב ו-`modsec_audit.log`: localSIEM לעולם אינו משנה ואינו מוחק לוג של Apache. להסרת ההתקנה:

```bash
# Debian 13 (Alpine: install-update-reinstall-alpine.sh)
curl -fsSL -H 'Accept: application/vnd.github.raw+json' https://api.github.com/repos/PYMEHackers/localSIEM/contents/deploy/install-update-reinstall-debian.sh | bash -s -- --uninstall
```

**התקנה מחדש.** כדי להתחיל מאפס בצעד אחד, הפעולה `--reinstall` מוחקת הכול באותו אופן ומתקינה את localSIEM מחדש (יש לציין שוב את האפשרויות):

```bash
# Debian 13 (Alpine: install-update-reinstall-alpine.sh)
curl -fsSL -H 'Accept: application/vnd.github.raw+json' https://api.github.com/repos/PYMEHackers/localSIEM/contents/deploy/install-update-reinstall-debian.sh | bash -s -- --reinstall --allow-from 203.0.113.10 --soc-token TOKEN
```

**2. המודולים.** תוכנית ההתקנה של localSIEM אינה מתקינה **אף מודול**: היא משאירה את localSIEM מוכן לקבל אותם, ועדכון שומר על אלה שכבר מותקנים (ועל הרשאת הקריאה ללוגים שלהם). מודולים מותקנים **רק מממשק האינטרנט**: מודולים › ניתנים להתקנה (סעיף 13), שם מוצגים המודולים של המאגר `localSIEM-modules` שעדיין אינם מותקנים; למאגר הזה אין תוכנית התקנה משלו. localSIEM מוריד ממנו את המודול, מעתיק את התיקייה שלו (`mod-<name>/` שם) אל `/opt/localsiem/modules/<name>/` (התיקיות `tests/` אינן מועתקות; מודול שמותקן שוב מקבל בחזרה את ההגדרות שהיו לו) ומפעיל מחדש את רכיב האיסוף. גם העדכון והסרת ההתקנה של מודולים נעשים מממשק האינטרנט: **עדכון**, כשבמאגר יש גרסה חדשה יותר, ו-**הסרת התקנה**, שניהם תחת מודולים › מותקנים (סעיף 13).

קריאת הלוגים של מודול דורשת root, ולכן, אחרי שהמודול מותקן, ממשק האינטרנט מציג בחלון דו-שיח את הפקודה שיש להריץ בתור root בשרת:

```bash
/opt/localsiem/venv/bin/python /opt/localsiem/webapp/backend/manage.py setup-modules
```

הפקודה מעניקה למשתמש `localsiem` הרשאת קריאה לתיקיות הלוגים שכל מודול מותקן מצהיר עליהן (`/var/log/apache2` עבור מודול Apache; סעיף 3.7), גם לקבצים של הרוטציות הבאות, מפעילה מחדש את localSIEM ומריצה את האבחון בתור `localsiem`. ניתן להריץ אותה שוב בכל עת. הרשאת הקריאה הזו, שהפקודה של localSIEM מעניקה, היא כל מה ש-root עושה עבור המודולים.

**התקנת מודול לעולם אינה מתקינה את התוכנה שהוא עוקב אחריה**, וגם לא שום דבר אחר: מודול עובד עם מה שכבר יש בשרת ולעולם אינו משנה דבר מחוץ ל-`/opt/localsiem/`. מודול חדש מתחיל כשהוא מופעל או כבוי, לפי מה שהחליט המחבר שלו, אלא אם לשרת חסר מה שהמודול צריך (עבור מודול Apache: Apache ו-ModSecurity 2): אז הוא מותקן **במצב כבוי**, ממשק האינטרנט מציין מה חסר, והמתג שלו נשאר נעול עד ש-**הגדרה מחדש** מוצאת את מה שחסר (סעיף 13). המצב שלו מופיע תחת **מודולים › מותקנים** (סעיף 13).

<a id="requirements"></a>
## 3. דרישות Apache ו-ModSecurity

אלה הדרישות של המודול Apache + ModSecurity. את Apache ואת ModSecurity 2 עצמם יש להתקין קודם: בלעדיהם לא ניתן להפעיל את המודול (סעיף 13). localSIEM לעולם אינו משנה בעצמו את התצורה של Apache, וגם לא את הלוגים של Apache, את הפורמט שלהם או את אופן כתיבתם: המודול קורא את הלוגים שהשרת כבר כותב ומסתגל אליהם. האבחון של המודול (סעיף 4) בודק כל דרישה: עבור ModSecurity עם ה-CRS שלו ו-`SecRuleEngine` (נקודה 1), `mod_unique_id` (נקודה 2) והרשאת הקריאה (נקודה 7) הוא מציג את קטע התצורה או את הפקודה המדויקים לכל דרישה חסרה, כדי שניתן יהיה להחיל אותם; את הלוגים (נקודות 3 עד 6) הוא רק מתאר, בלי להציע לשנות אותם.

1. **ModSecurity 2 עם OWASP CRS**, עם `SecRuleEngine On` או `DetectionOnly`. שתי האפשרויות עובדות: עם `DetectionOnly` שום דבר אינו נחסם, ולכן כל התאמה נשלחת ל-SOC.
2. **`mod_unique_id`**, ש-ModSecurity 2 צריך כדי לעבוד בכלל (בלעדיו הוא אינו בודק דבר; Alpine אינו טוען אותו כברירת מחדל) ושמצרף את שלוש הרשומות של כל בקשה.
3. **לוג גישה**, כפי ש-Apache כותב אותו. כל פורמט עובד (`combined`, `vhost_combined`, `common`, או כל `LogFormat` של התצורה): כל שורה משויכת לבקשה שלה לפי ה-IP של הלקוח, השיטה, ה-URI, הסטטוס והזמן («קורלציה חלשה»), וה-vhost נלקח מ-`%v` או, בלעדיו, מכותרת ה-Host ומהפורט של רשומת הביקורת. כשהפורמט כולל גם אלפיות שנייה, `%v` ו-`%{UNIQUE_ID}e` (כמו השורות `localsiem_combined` שחלק מהשרתים כבר כותבים), כל שורה משויכת לבקשה שלה לפי `UNIQUE_ID`, ועם `%D` localSIEM מקבל גם את משך הבקשה. לוג גישה שבפורמט שלו חסרים ה-IP של הלקוח, הזמן, שורת הבקשה או הסטטוס נקרא כפי שהוא, אבל לא ניתן לשייך את השורות שלו לבקשות שלהן: את הבקשות האלה רואים בלוג הביקורת של ModSecurity. `CustomLog` שבפורמט שלו אין שום הנחיה כותב את אותו טקסט בכל שורה ואינו נקרא.
4. **`mod_remoteip`**, שקובע איזו IP נרשמת בלוגים. אם אתר האינטרנט נמצא מאחורי proxy או מאזן עומסים ו-Apache אינו משתמש בו, הלוגים מכילים את ה-IP של ה-proxy, וכך גם ההתראות והכללים לפי IP: האבחון ואזהרת התקינות «חסרה ה-IP האמיתית של הלקוח» (סעיף 15) מציינים זאת.
5. **לוג הביקורת של ModSecurity**, כפי ש-ModSecurity כותב אותו: טורי או מקבילי, JSON או הפורמט הרגיל שלו, עם החלקים שיש בו. בלעדיו (`SecAuditEngine Off` או ללא `SecAuditLog`) localSIEM מחליט על סמך `error.log` בלבד, ובכרטיס הבקשה אין כותרות או רשימת כללים. בלי חלק `H` לא ניתן לקרוא ממנו את הפעולה שננקטה. חלק `E` (גוף התגובה), אם הוא נרשם, לעולם אינו נשלח ל-SOC; חלק `K` (הטקסט המלא של כל כלל שהורץ) אינו נשמר. בסוג המקבילי (קובץ לכל טרנזקציה), ModSecurity יוצר בדרך כלל את הקבצים בהרשאות 600, ו-localSIEM קורא אותם רק אם `localsiem` יכול לקרוא אותם (נקודה 7).
6. **מיסוך במקור**: אם ModSecurity אינו ממסך את לוג הביקורת בדיסק (פעולות ה-`sanitise` שלו), הקובץ הזה עלול להכיל סיסמאות וקובצי cookie; localSIEM ממסך אותם לפני שהוא שומר אותם, והם לעולם אינם נשלחים ל-SOC.
7. **הרשאת קריאה למשתמש `localsiem`** ללוגים. הפקודה ל-root של סעיף 2 (`manage.py setup-modules`) מעניקה אותה לתיקיות שהמודולים המותקנים מצהירים עליהן (`/var/log/apache2` עבור מודול Apache), ותוכנית ההתקנה של localSIEM מעניקה אותה שוב בכל עדכון: ב-Debian היא מוסיפה את `localsiem` לקבוצה `adm` וכמו ב-Alpine, מעניקה ל-`localsiem` הרשאת קריאה לתיקיות האלה באמצעות ACL, כולל ACL ברירת מחדל כדי שגם הקבצים של הרוטציות הבאות יהיו קריאים. גם לוגים שמוסיפים ידנית בתיקייה אחרת (סעיף 13) צריכים את ההרשאה הזו, לדוגמה `setfacl -m g:localsiem:rx /srv/logs`, `setfacl -d -m g:localsiem:r /srv/logs` ו-`setfacl -m g:localsiem:r /srv/logs/*.log`. localSIEM רק קורא את הלוגים: הוא לעולם אינו כותב בהם, ואינו מבצע להם רוטציה, קיצוץ, העברה או מחיקה. כשהוא מתחיל לעקוב אחר לוג (בהפעלה הראשונה, אחרי התקנה או הפעלה של מודול, או ברגע ש-root מעניק לו הרשאת קריאה) הוא מתחיל מסופו: מה שכבר היה בלוג הוא היסטוריה ולעולם אינו מפיק התראה; רק הלוג של vhost שנוצר מאוחר יותר נקרא מתחילתו (כשגודלו עד 5 MB).

<a id="doctor"></a>
## 4. האבחון

לכל מודול יש אבחון משלו. האבחון של מודול Apache בודק כל דרישה של סעיף 3 ומציג את קטע התצורה או את הפקודה שמתקנים כל דרישה חסרה; את הלוגים (פורמט, `mod_remoteip`, לוג ביקורת, מיסוך) הוא רק מתאר, בלי להציע לשנות אותם, והוא מפרט את המקורות שנמצאו (ואת אלה שאין באפשרותו לקרוא, כמו לוגים דרך צינור). הוא רץ בסוף כל התקנה של localSIEM ובסוף הפקודה ל-root של סעיף 2, מופיע בדף של כל מודול (**מודולים › מותקנים › הגדרה**, סעיף 13, עם הכפתור «גילוי מחדש והרצת האבחון»), וניתן להריץ אותו בכל עת עבור כל מודול מופעל:

```bash
runuser -u localsiem -- /opt/localsiem/venv/bin/python /opt/localsiem/webapp/backend/manage.py doctor   # Debian
su -s /bin/sh localsiem -c "/opt/localsiem/venv/bin/python /opt/localsiem/webapp/backend/manage.py doctor"   # Alpine
```

הסימן `✓` פירושו תקין, `!` עובד עם מגבלות, `✗` חייב תיקון, `·` רלוונטי רק במצבים מסוימים (בצבע במסוף; היכן שלא ניתן לכתוב UTF-8: `+`, `!`, `x` ו-`-`). מודול שלא ניתן לטעון מוצג ראשון בתור `✗ Module <name> not loaded: <reason>`. למודול כבוי אין אבחון: אם יש לו דרישות (סעיף 13), האבחון מציג אותן במקום זאת, כדי שיהיה ברור אם ניתן להפעיל אותו.

<a id="soc"></a>
## 5. חיבור ל-SOC

חיבור localSIEM ל-SOC הוא אופציונלי. בלי SOC (אין טוקן, או ש-**שליחת התראות ל-SOC** כבויה), localSIEM פועל בכוחות עצמו: הוא שומר כל התראה בלשונית **התראות** בתור «לא נשלחה» ולעולם אינו שולח אותן מאוחר יותר, גם לא כשמגדירים SOC לאחר מכן: מאותו רגע רק ההתראות החדשות נשלחות אליו. הערוצים (Telegram) פועלים עם SOC או בלעדיו.

מנהל המערכת של ה-SOC:

1. יוצר טוקן קליטה עבור הלקוח (הוא מוצג פעם אחת בלבד) ומוסר אותו. יש להגדיר אותו עם `--soc-token` או תחת **ניהול › SOC**.
2. מגדיר בתור **כתובת ה-SIEM** של הלקוח את `https://<server>:<port of localSIEM>` (תוכנית ההתקנה מציגה אותה, וכך גם ניהול › SOC). האנליסט שאחראי על התראה משתמש בקישור הזה כדי להגיע ולחקור.
3. מוסר את כתובות ה-IP היוצאות של ה-SOC: יש להוסיף אותן לכתובות ה-IP המורשות (`--allow-from` או ניהול › הגדרות) ו**לפתוח את הפורט בחומת האש רק להן ולמנהלי המערכת שלך**.

כל 5 דקות localSIEM שולח **אות חיים**. אם ה-SOC אינו מקבל לא התראות ולא אותות חיים במשך זמן מה (60 דקות כברירת מחדל), הוא מזהיר את הצוות שלו. ההתראות ממתינות בתור קבוע: ניתוק רשת או הפעלה מחדש אינם מאבדים אף אחת, ושליחה חוזרת של התראה לעולם אינה יוצרת כפילות שלה ב-SOC. אם ה-SOC עונה שהלקוח ניצל את כל מספרי ההתראות שלו, localSIEM מפסיק לשלוח, שומר על התור ומציג זאת תחת ניהול › SOC.

כל התראה נושאת שם כלל יציב, תיאור עם השאילתה המדויקת להדבקה בחיפוש של localSIEM, ופרטים: vhost, ה-IP של הלקוח, שיטה, URI (ממוסך), תשובה, user agent, נתוני ModSecurity (מנוע, פעולה, שלב, ציון, סף, כללים, נתונים שהתאימו), הקבוצה (כמות, הופעה ראשונה ואחרונה, דוגמאות של `UNIQUE_ID`) ו**ההקשר** של ה-IP: בקשות ובקשות חסומות בשעה האחרונה, כללים שחסמו והפעם הראשונה שבה היא נראתה.

<a id="signin"></a>
## 6. התחברות וחשבונות

יש לפתוח את `https://<server>:10443/`: דף ההתחברות הוא הטופס בלבד, עם הלוגו, שם המשתמש, הסיסמה, **המשך** ומתחתיו השפה וערכת הנושא. את החשבונות יוצר מנהל מערכת; אין הרשמה פתוחה. לסיסמאות יש לפחות 8 תווים. **אימות דו-שלבי** כבוי כברירת מחדל; כשמנהל מערכת מפעיל אותו (ניהול › הגדרות, סעיף 14) הוא חובה לכל החשבונות: בהתחברות הבאה יש לסרוק את קוד ה-QR באפליקציית אימות (Google Authenticator, Microsoft Authenticator, Aegis, FreeOTP...; localSIEM מופיע בה בתור «PYMEHackers localSIEM») ולהקליד את הקוד שלה, ומאז כל התחברות מבקשת את הקוד של האפליקציה. אחרי כמה ניסיונות כושלים, ההתחברות ננעלת לכמה דקות.

**גישה ישירה עם טוקן.** מנהל מערכת יכול למסור לאנליסט כתובת URL לגישה, `https://<server>:10443/auth/login/auto?token=...` (משתמשים › טוקני גישה, סעיף 14). פתיחתה מכתובת מורשית מחברת מיד, בלי סיסמה ובלי גורם שני, ופותחת את הסקירה הכללית של לוח הבקרה של המשתמש; הוספת `&next=/user/dashboard/search/?q=...` פותחת דף אחר של האתר. אם הטוקן אינו פועל, דף ההתחברות מציין מדוע: טוקן לא ידוע, שפג תוקפו או מבוטל, או שהחשבון מושבת או שאינו עוד אנליסט. יש לשמור על כתובת ה-URL כמו על סיסמה: כל מי שמחזיק בה יכול להתחבר עם החשבון הזה עד שתוקפה יפוג או שהיא תבוטל. כל התחברות, עם סיסמה או עם טוקן, וכל ניסיון כושל נרשמים (התחברויות, סעיף 14).

אחרי ההתחברות נפתחת הלשונית **סקירה כללית** של לוח הבקרה (סעיף 7). קישור לחיפוש (לדוגמה מה-SOC) פותח את דף ההתחברות אם צריך, ולאחר מכן **את אותו חיפוש עם הפרמטרים שלו**.

תפקידים: **אנליסט** (עובד בלוח הבקרה של המשתמש: סקירה כללית, חיפוש, תצוגה בזמן אמת, התראות, מצב המודולים והחשבון) ו**מנהל מערכת** (עובד בלוח הבקרה של מנהל המערכת: אותו דבר, ובנוסף התצורה של המודולים והניהול). השפה (de-DE, en-GB, en-US, es-AR, es-ES, fr-FR, he-IL, hi-IN, it-IT, ja-JP, ko-KR, pt-BR, pt-PT, ru-RU, zh-CN), ערכת הנושא (לפי המערכת, בהירה או כהה) ושעון ה-UTC נמצאים בשורת הכותרת של כל דף בלוחות הבקרה; בדף ההתחברות הם נמצאים מתחת ל-**המשך**, ומתחילים עם אלה שנבחרו לאחרונה בדפדפן הזה (אם לא נבחרו, אלה של הדפדפן ושל המערכת). השפה שמוצגת בעת לחיצה על **המשך** הופכת לשפת החשבון: לוחות הבקרה שומרים עליה, בכל דפדפן, עד שמשנים אותה. הזמנים תמיד ב-UTC בפורמט המקורי `2026/10/29@13:59:59.723`. הקבצים ש-localSIEM כותב (הייצואים, `/root/webapp-credentials.txt`, הלוג של תוכנית ההתקנה) וההתראות שהוא שולח ל-SOC משתמשים בפורמט האחסון `2026-10-29@13-59-59.723`, גם הוא ב-UTC.

<a id="dashboards"></a>
## 7. שני לוחות הבקרה

לכל תפקיד יש לוח בקרה משלו; הכתובת מראה באיזה מהם נמצאים. בסרגל הצד יש למעלה את הלוגו, את הלשוניות (קו מפריד בין קבוצה לקבוצה) ולמטה את **התנתקות**.

| | לוח הבקרה של מנהל המערכת | לוח הבקרה של המשתמש |
|---|---|---|
| מי | מנהלי מערכת | אנליסטים |
| כתובת | `/admin/dashboard/<tab>/` | `/user/dashboard/<tab>/` |
| לשוניות | סקירה כללית, חיפוש, בזמן אמת, התראות; מודולים (מותקנים וניתנים להתקנה), משתמשים (חשבונות וטוקני גישה), SOC, ערוצים (כללי ו-Telegram), הגדרות, ביקורת חיפושים, התחברויות; חשבון | סקירה כללית, חיפוש, בזמן אמת, התראות, מודולים (מצב בלבד), חשבון |

לכל לשונית יש כתובת משלה (לדוגמה `/admin/dashboard/logins/`), ו-`/admin/dashboard/` או `/user/dashboard/` פותחות את הסקירה הכללית. גם לחלקים של לשונית יש כתובות משלהם: `/admin/dashboard/users/` פותחת את `/admin/dashboard/users/accounts/`, וטוקני הגישה נמצאים ב-`/admin/dashboard/users/tokens/`; `/admin/dashboard/modules/` פותחת את `/admin/dashboard/modules/installed/`, והמודולים הניתנים להתקנה נמצאים ב-`/admin/dashboard/modules/installable/`. כתובת של לוח הבקרה האחר מובילה לאותה לשונית בלוח הבקרה של מי שפותח אותה: מנהל מערכת שפותח קישור אל `/user/dashboard/search/?q=...` (הקישור הרגיל של ה-SOC) מקבל את אותו חיפוש ב-`/admin/dashboard/search/`; אנליסט שפותח לשונית ניהול מקבל את הסקירה הכללית של לוח הבקרה של המשתמש.

**מה שאנליסטים רואים.** כל מה שנדרש לחקירה: הסקירה הכללית, החיפושים עם כרטיסי הבקשות שלהם, התצוגה בזמן אמת, ההתראות ומצב כל מודול (מופעל או כבוי, פועל או לא, והמונים שלו). הם אינם יכולים להפעיל או לכבות מודולים, להגדיר אותם, לראות את האבחון או את הכללים שלהם, וגם לא לנהל משתמשים, טוקני גישה, את החיבור ל-SOC, את ההגדרות, את ביקורת החיפושים או את רישום ההתחברויות.

<a id="overview"></a>
## 8. סקירה כללית

הלשונית הראשונה בשני לוחות הבקרה. היא מתרעננת כל 15 שניות ומציגה:

- **אירועים (24 שעות)**, עם מספר האירועים שהפיקו התראה; **נחסמו (24 שעות)**, מה ש-ModSecurity כבר טיפל בו (נשמר, ללא התראה); **התראות (24 שעות)**, עם מספר ההתראות שממתינות ל-SOC; ו-**מודולים פועלים**, המודולים המופעלים שנמצאים במצב «פעיל ותקין» מתוך המודולים המופעלים (בירוק כשכולם פועלים).
- **הפעילות ב-24 השעות האחרונות**: אירועים לשעה; החלק הכחול בכל עמודה הוא מה ש-ModSecurity חסם. לחיצה על שעה פותחת את החיפוש של האירועים שלה.
- **מצב המודולים**: כל מודול עם המצב שלו (סעיף 13) ומה שהוא קורא; «צפייה במודולים» פותח את הלשונית מודולים.
- **מערכת**: אם רכיב האיסוף פועל (והגרסה שלו), ממתי, מצב החיבור ל-SOC, אות החיים האחרון, ההתראות הממתינות ל-SOC, השטח הפנוי בדיסק וגודל מסד הנתונים ביחס למקסימום שלו.
- **ההתראות האחרונות**: שש ההתראות האחרונות (חומרה, כלל, IP, כמות, סטטוס, הופעה אחרונה); «צפייה בכל ההתראות» פותח את הלשונית התראות.

<a id="search"></a>
## 9. חיפוש

בלשונית **חיפוש** יש שדה חיפוש אחד וטווח זמן (15 הדקות האחרונות, השעה האחרונה, 24 השעות האחרונות, 7 הימים האחרונים, 30 הימים האחרונים, או טווח מותאם אישית בפורמט המקורי).

| תחביר | משמעות |
|---|---|
| `word` | חיפוש טקסט מלא בטקסט המקורי (הממוסך), גם לאחר פענוח URL |
| `"exact phrase"` | ביטוי |
| `field:value` | שדה השווה לערך (שדות טקסט אינם מבחינים בין אותיות רישיות לקטנות) |
| `field:*part*` | תווים כלליים |
| `status:>=500`, `status:400..499`, `status:4xx` | השוואות וטווחים בשדות מספריים |
| `a b` / `a AND b`, `a OR b`, `NOT a` / `-a`, `( )` | אופרטורים וסוגריים |

| קבוצה | שדות |
|---|---|
| רשת | `ip`, `vhost`, `host` |
| בקשה | `method`, `uri`, `path`, `query`, `status`, `bytes`, `duration` (מיקרו-שניות), `ua`, `referer` |
| מוצא | `uid` (UNIQUE_ID), `module`, `source` (`access`/`error`/`audit`) |
| ModSecurity | `rule` (מזהה CRS, או `localsiem:<rule>`), `category`, `phase`, `score`, `engine` (`on`/`detection-only`) |
| התראות | `severity`, `action` (`blocked`/`none`), `alert` (קוד SOC), `sent` (`yes`/`no`) |
| איכות | `parse` (`ok`/`partial`/`unparsed`) |

דוגמאות:

- `ip:203.0.113.7` — כל מה שקשור ל-IP אחת
- `rule:942100` — בקשות שהתאימו לכלל ה-CRS הזה
- `status:200 action:none category:sqli` — הזרקות SQL שלא נחסמו וקיבלו 200
- `uri:*wp-login*`
- `"union select"`
- `uid:ZTx1kH8AAQEAAB2gTkAAAAAB` — בקשה אחת
- `alert:c00007a0001F` — הבקשות של התראת SOC אחת
- `(category:sqli OR category:xss) sent:no -status:404`

קטגוריות: `sqli`, `xss`, `lfi`, `rfi`, `rce`, `php`, `java`, `fixation`, `generic`, `protocol`, `multipart`, `scanner`, `method`, `data-leakage`, `webshell`, ואלה של הכללים של localSIEM: `bruteforce`, `enumeration`, `sensitive-file`, `db-error`, ובנוסף `health-*`.

שגיאת תחביר מוצגת מתחת לשדה, עם המיקום של הטעות. חיפוש שנמשך יותר מהמגבלה שלו (5 שניות) מבקש לצמצם את הטווח.

דף התוצאות מציג:

- **ההיסטוגרמה** לאורך זמן; החלק הכחול בכל עמודה הוא מה ש-ModSecurity חסם. גרירה מעל העמודות (או לחיצה על אחת מהן) מצמצמת את הטווח.
- **סיכומים** של השאילתה: כתובות IP עם הכי הרבה בקשות, הנתיבים המבוקשים ביותר, קודי HTTP והכללים השכיחים ביותר. לחיצה על ערך מוסיפה אותו לשאילתה.
- **טבלת התוצאות** (זמן, מקור, IP, שיטה, URI, קוד, פעולה, כללים, התראה), החדשות ביותר קודם, עם «טעינת עוד».
- **ייצוא** ל-CSV או ל-JSON (נתונים ממוסכים, עד 10 000 שורות, זמנים בפורמט האחסון `2026-10-29@13-59-59.723`) ו-**העתקת קישור** (עם זמנים מוחלטים). פורמט הקישור הוא `/user/dashboard/search/?q=<query>&from=<native time>&to=<native time>` (`/admin/dashboard/search/...` כשמנהל מערכת מעתיק אותו); קישור של כל אחד מלוחות הבקרה עובד לשני התפקידים.

כל חיפוש וכל ייצוא נרשמים (מי, מה, מתי) וגלויים למנהלי המערכת: הלוגים מכילים מידע אישי.

<a id="card"></a>
## 10. כרטיס הבקשה והפיבוטים

לחיצה על שורה פותחת את הכרטיס של הבקשה: זמן, vhost, ה-IP של הלקוח, שיטה, URI, קוד, גודל, משך, user agent, `UNIQUE_ID`, קורלציה, הפעולה שננקטה, מנוע ModSecurity, שלב, ציון וסף, קטגוריה, חומרה והתראות; ועבור כל רשומה, התוכן המנותח שלה: הכללים שהתאימו עם ההודעה והנתונים שלהם, כותרות הבקשה והגוף הממוסך, כותרות התגובה, שורות השגיאה והשורה המקורית. המודול של כל רשומה מוסיף את מה שהוא יודע להציג (מודול Apache משחזר את הכותרות ואת הגוף מרשומת הביקורת).

הערות בכרטיס: תשובת 403 ללא כל עקבות של ModSecurity מסומנת כ**מפוקפקת** (היא אינה נספרת כחסימה); **קורלציה חלשה** פירושה ששורת הגישה שויכה לבקשה שלה לפי ה-IP של הלקוח, השיטה, ה-URI, הסטטוס והזמן, מפני שבלוג הגישה אין `UNIQUE_ID`; **שגיאת מסד נתונים** פירושה ששגיאה כזו הופיעה עבור הבקשה.

פיבוטים: **IP זו** (כל הפעילות שלה), **±5 דק'** (ציר הזמן סביב הבקשה), **כלל …** (כל כלל שהתאים), **קטגוריה זו**, **UNIQUE_ID זה**.

<a id="live"></a>
## 11. תצוגה בזמן אמת

הלשונית **בזמן אמת** מציגה את האירועים החדשים ברגע שרכיב האיסוף שומר אותם (אחרי חלון הקורלציה של 5 שניות), החדשים ביותר למעלה. המסנן משתמש בתחביר החיפוש. **השהיה** עוצרת את העדכונים; בחידוש, התצוגה ממשיכה מהאירוע החדש ביותר.

<a id="alerts"></a>
## 12. התראות

הלשונית **התראות** מציגה את ההתראות ש-localSIEM הפיק: קוד SOC, חומרה, כלל, IP, vhost, כמות, הופעה ראשונה ואחרונה, וסטטוס:

| סטטוס | משמעות |
|---|---|
| בחוצץ | אוספת את פרץ האירועים (60 שניות) לפני היציאה |
| בתור | ממתינה ל-SOC (הרשת אינה זמינה, ה-SOC אינו עונה) |
| נשלחה | ה-SOC קיבל אותה; הקוד שלה מוצג |
| נדחתה | ה-SOC סירב להתראה הזו; שאר התור ממשיך. ניתן להחזיר אותה לתור מתוך ניהול › SOC. |
| לא נשלחה | לא היה SOC מוגדר, או שהשליחה אליו כובתה: ההתראה נשארת ב-localSIEM ולעולם אינה נשלחת מאוחר יותר (ה-SOC הוא אופציונלי, סעיף 5) |

לחיצה על שורה מציגה את התיאור, את **הבקשות של ההתראה** (עד 50, הישנות ביותר קודם, כמו בחיפוש: לחיצה על אחת מהן פותחת את כרטיס הבקשה שלה, עם הבקשה, הכותרות שלה, כללי ModSecurity והשורות המקוריות), את החלון, את ה-`external_id` ואת ההתראה המדויקת שנשלחה ל-SOC. **חיפוש** פותח את החיפוש של הקבוצה. כל עוד התראה פתוחה, הרשימה אינה מתרעננת.

<a id="modules"></a>
## 13. מודולים

בלוח הבקרה של מנהל המערכת, ללשונית **מודולים** יש שני חלקים, לכל אחד כתובת משלו: **מותקנים** (`/admin/dashboard/modules/installed/`), שנפתח כברירת מחדל (`/admin/dashboard/modules/` מוביל אליו), ו-**ניתנים להתקנה** (`/admin/dashboard/modules/installable/`), שבו מתקינים מודולים (בהמשך). לאנליסטים יש רק את רשימת המודולים המותקנים, בלי חלקים (`/user/dashboard/modules/`).

החלק **מותקנים** מציג את המודולים המותקנים, שורה לכל מודול, לכל הרוחב, בפריסה זהה לזו של הכותרת של דף המודול: למעלה השם, המזהה והגרסה, ומתחתם **המצב** שלו, תקציר, הסיבות למצבו ואם הוא מופעל, המונים שלו: מקורות בקריאה, שורות בשעה האחרונה, נתונים אחרונים, אירועים ובקשות חסומות ב-24 השעות האחרונות ותוצאת האבחון שלו. מנהלי מערכת רואים גם את המתג ליד השם, ובתחתית השורה את הכפתורים שלו. הדף מתרענן כל 10 שניות. כשאין אף מודול מותקן מופיע «ניתן להתקין מודולים מהלשונית ניתנים להתקנה.» (לאנליסטים: «אין מודולים מותקנים. מנהל מערכת מתקין אותם תחת מודולים › ניתנים להתקנה.»).

| מצב | משמעות |
|---|---|
| פעיל ותקין | מופעל, נטען על ידי רכיב האיסוף וקורא את המקורות שלו. אזהרות של האבחון מוצגות כהערות ואינן משנות את המצב. |
| פעיל, עם אזהרות | מופעל, אבל בלי מקורות, עם מקור שעדיין אינו קיים, או שהותקן אחרי שרכיב האיסוף הופעל (יש להפעיל מחדש את השירות `localsiem`). |
| שגיאה | אינו נטען (הסיבה מוצגת), האבחון שלו מדווח על שגיאה, או שלא ניתן לקרוא אחד המקורות (הרשאות המשתמש `localsiem`, סעיף 3.7). |
| השינוי מוחל… | הופעל או כובה זה עתה; רכיב האיסוף מחיל את השינוי (כמה שניות). |
| כבוי | כבוי: localSIEM אינו קורא את הלוגים שלו ואינו שולח את ההתראות שלו. מה שכבר נשמר נשאר. עם הסיבה «לשרת זה חסר מה שהמודול צריך: …», הוא הותקן בלי הדרישות שלו ועדיין לא ניתן להפעיל אותו (פרטים תחת דרישות והגדרה מחדש, בהמשך). |
| לא ידוע | רכיב האיסוף אינו פועל (שירות `localsiem`): אף אחד אינו קורא דבר. |

**אנליסטים** רואים רק את הרשימה הזו. ל**מנהלי מערכת** יש גם, בכל שורה:

- **המתג** של כל מודול, להפעלה או לכיבוי שלו. כיבוי מבקש אישור. השינוי חל מיד, בלי להפעיל מחדש שום דבר. כל עוד לשרת חסר מה שמודול צריך, המתג שלו נעול («כבוי: חסרות דרישות»).
- **הגדרה**, שפותח את הדף של המודול (`/admin/dashboard/modules/installed/<name>/`; הכתובת הישנה `/admin/dashboard/modules/<name>/` מובילה אליו):
  - הכותרת עם המצב, התיקייה שבה המודול מותקן, המתג, «חזרה למודולים המותקנים» (חוזר אל מותקנים) ו-«גילוי מחדש והרצת האבחון»; עבור מודול עם דרישות, גם הכפתור «הגדרה מחדש», וכל עוד המודול כבוי או שחסרה דרישה, החלק **דרישות** שלו (בהמשך);
  - **הגדרות**: הטופס של ההגדרות של המודול עצמו; «שמירת ההגדרות» מחילה אותן מיד;
  - **מקורות**: הלוגים שהוא קורא (סוג, נתיב, vhost, שורות ושורות שלא נותחו בשעה האחרונה, נתונים אחרונים, מצב) ומתחתם, הלוגים שהוא מצא אבל אינו קורא, עם הסיבה;
  - **אבחון**: בדיקות הדרישות שלו, עם קטע התצורה או הפקודה שמתקנים כל דרישה חסרה וכפתור «העתקה» (הלוגים רק מתוארים);
  - **כללים**: כל כלל של המודול עם המתג שלו («פעיל»), חומרה, סף וחלון (סף וחלון רק עבור כללי סף ורצף); «שמירת הכללים» מחילה אותם מיד.
- **עדכון**, כשבמאגר `localSIEM-modules` יש גרסה חדשה יותר של המודול. בכל פתיחה של מותקנים, localSIEM בודק את המאגר: בינתיים מופיע «מתבצעת בדיקה במאגר לאיתור גרסאות חדשות יותר…», ואם הבדיקה נכשלת, «לא ניתן היה לבדוק במאגר אם יש גרסאות חדשות יותר: <error>», והרשימה פועלת כרגיל. כדי שהמאגר לא יורד בכל ביקור, הדפדפן משתמש שוב בתשובה שלו במשך 10 דקות; «בדיקת המאגר», בחלק ניתנים להתקנה, מוריד אותו תמיד מחדש, והתקנה, עדכון או הסרת התקנה של מודול מבטלים את התשובה השמורה. הרענון כל 10 שניות לעולם אינו מוריד אותו. מודול שיש לו גרסה חדשה יותר מציג בשורה שלו את ההודעה «במאגר יש גרסה X (הגרסה המותקנת היא Y).» עם הכפתור **עדכון**. אם הגרסה הזו דורשת localSIEM חדש יותר, אין בהודעה כפתור והיא מציינת זאת: «במאגר יש גרסה X, אבל היא דורשת localSIEM Z ומעלה: יש לעדכן את localSIEM כדי להתקין אותה.» **עדכון** מבקש אישור («עדכון המודול»): localSIEM מוריד את הגרסה החדשה מהמאגר, מחליף בה את הגרסה המותקנת ומפעיל מחדש את רכיב האיסוף; ההגדרות שלו נשמרות, והמודול נשאר מופעל או כבוי כפי שהיה. בזמן הפעולה, הכפתור מציג «מתבצע עדכון…»; בסיום, הודעה מציינת «<מודול> עודכן לגרסה X.» חלון דו-שיח, «<מודול> עודכן», נפתח רק כשיש עוד משהו לעשות: אם הגרסה החדשה קוראת לוגים אחרים, הוא מציג את הפקודה ל-root (`manage.py setup-modules`, סעיף 2, עם «העתקה»); אם רכיב האיסוף לא הגיב, הוא מבקש להפעיל מחדש את השירות `localsiem`.
- **הסרת התקנה**, בשורה של כל מודול מותקן (גם של מודול שאינו נטען) ובדף שלו. אחרי האישור, localSIEM מוחק את `/opt/localsiem/modules/<name>/` ומפעיל מחדש את רכיב האיסוף בלעדיו: הוא מפסיק לקרוא את הלוגים שלו ולשלוח את ההתראות שלו. עדיין ניתן לחפש את האירועים וההתראות שכבר נשמרו, וההגדרות שלו (והשינויים בכללים שלו) נשארות ב-`settings.json`, כך שהן חוזרות אם מתקינים אותו שוב. הרשאת הקריאה ש-root העניק ל-`localsiem` ללוגים שלו אינה נלקחת בחזרה; אם אף מודול אחר אינו קורא את התיקייה הזו, ניתן להסיר אותה ידנית, לדוגמה `setfacl -R -x g:localsiem /var/log/apache2` ו-`setfacl -d -x g:localsiem /var/log/apache2`.

בחלק **ניתנים להתקנה** (למנהלי מערכת בלבד) יש את הכרטיס «מודולים הניתנים להתקנה»: המודולים של המאגר `localSIEM-modules` (כברירת מחדל `https://github.com/PYMEHackers/localSIEM-modules`, הענף `main`; האפשרויות `--modules-repository` ו-`--modules-ref` של תוכנית ההתקנה משנות אותו) שעדיין אינם מותקנים בשרת זה. «בדיקת המאגר» מוריד אותו ומציג את המודולים האלה, כל אחד עם השם, המזהה, הגרסה והתקציר שלו ועם הכפתור או ההערה שלו:

| כפתור או הערה | משמעות |
|---|---|
| דרישות | מציג את מה שהמודול צריך בשרת ואת הפקודות שמתקינות אותו (בהמשך) |
| התקנה | מתקין את המודול |
| דורש localSIEM X ומעלה | לא ניתן להתקין אותו: יש לעדכן קודם את localSIEM |
| המודול שבמאגר אינו חוקי | לא ניתן להתקין אותו |

**דרישות** פותח את חלון הדו-שיח «<מודול>: דרישות», עם מה שהמודול צריך בשרת והפקודות שמתקינות אותו, כפי שהמודול עצמו מצהיר עליהם (`install_requirements` של ה-`module.json` שלו). התקנת מודול לעולם אינה מתקינה את התוכנה שהוא עוקב אחריה, ולכן יש להריץ אותן בשרת **לפני** התקנת המודול. חלון הדו-שיח מציג את הפקודות עבור המערכת של שרת זה («שרת זה: Debian GNU/Linux 13 (trixie)») פעמיים, כל אחת עם «העתקה»: **בתור root** ו-**עם sudo** (אותן פקודות עם `sudo` לפניהן), כדי שניתן יהיה להדביק אותן במסוף של השרת בתור root או בתור משתמש המורשה להשתמש ב-sudo. ההערות של המודול מופיעות ראשונות (לדוגמה, שאין ל-Alpine חבילה של ModSecurity 2). אם המודול אינו מצהיר על פקודות עבור המערכת של שרת זה, חלון הדו-שיח מציג את אלה של כל המערכות שהוא מצהיר עליהן (Debian ו-Alpine); אם הוא אינו מצהיר על אף אחת, מופיע «מודול זה אינו מצהיר על שום דבר שיש להתקין בשרת.». localSIEM לעולם אינו מריץ את הפקודות האלה.

אם כל המודולים של המאגר כבר מותקנים, מופיעה הודעה על כך («כל המודולים שבמאגר כבר מותקנים.»). מודולים שכבר מותקנים לעולם אינם מופיעים ברשימה הזו: הם מתעדכנים בחלק מותקנים (**עדכון**, למעלה). ממשק האינטרנט אינו מתקין מחדש מודול ואינו מתקין גרסה ישנה יותר שלו: כדי להתקין מודול מחדש, יש להסיר את התקנתו ולהתקין אותו שוב כאן (ההגדרות שלו נשמרות).

הרשימה הזו היא הדרך היחידה להתקין מודולים. localSIEM מוריד את המודול, בודק את ה-`module.json` שלו, מעתיק את התיקייה שלו (`mod-<name>/` במאגר) אל `/opt/localsiem/modules/<name>/` (בלי התיקייה `tests/` שלו; מודול שמותקן שוב מקבל בחזרה את ההגדרות שהיו לו) ומפעיל מחדש את רכיב האיסוף, שטוען אותו תוך כמה שניות. המודול יוצא מהרשימה, וחלון דו-שיח, «<מודול> הותקן», מציין מה הלאה:

- כדי לאפשר ל-`localsiem` לקרוא את הלוגים של המודול נדרש root, ולכן חלון הדו-שיח מציג את **הפקודה שיש להריץ בתור root** בשרת, עם כפתור «העתקה»: `manage.py setup-modules` (סעיף 2), שמעניקה את הרשאת הקריאה ומפעילה מחדש את localSIEM. עד שהפקודה מורצת, המודול עשוי להציג «שגיאה» מפני שלא ניתן לקרוא את הלוגים שלו.
- אם בהתקנה הראשונה שלו לשרת חסר מה שהמודול צריך, המודול מותקן במצב כבוי וחלון הדו-שיח מפרט את מה שחסר במקום הפקודה, עם ההנחיה לפתוח את המודול בחלק מותקנים (**הגדרה**) וללחוץ על **הגדרה מחדש** כשהחסר כבר קיים (בהמשך).

בחלון הדו-שיח יש שני כפתורים: «סגירה» ו-«צפייה במודולים המותקנים», שפותח את מותקנים. השרת צריך גישה ל-GitHub (HTTPS) עבור הרשימה הזו ועבור הבדיקה של גרסאות חדשות יותר בחלק מותקנים.

**דרישות והגדרה מחדש.** התקנת מודול לעולם אינה מתקינה את התוכנה שהוא עוקב אחריה. מודול יכול להצהיר על מה שחייב להיות בשרת לפני שניתן להפעיל אותו: מודול Apache צריך את Apache (התצורה שלו: `apache2.conf`, `httpd.conf` או הקובץ של ההגדרה **קובץ התצורה של Apache**) ואת ModSecurity 2 טעון (`mod_security2`; ModSecurity 3 אינו נחשב). אם הם חסרים בהתקנה הראשונה שלו, המודול מותקן **במצב כבוי** («כבוי», עם הסיבה «לשרת זה חסר מה שהמודול צריך: …») והמתג שלו **נעול**. הדף שלו מפרט את הדרישות שלו כמו האבחון (כותרת, פירוט והפקודה שמתקינה את מה שחסר, עם «העתקה»), גם כשהוא כבוי. אחרי התקנת מה שחסר (ואם Apache נמצא במקום לא סטנדרטי, אחרי הגדרת **קובץ התצורה של Apache** ושמירת ההגדרות), יש ללחוץ על **הגדרה מחדש**: localSIEM מחפש אותו שוב לפי ההגדרות השמורות.

- אם הוא מוצא הכול, הוא משחרר את המתג אבל אינו מפעיל את המודול: ההפעלה נעשית ידנית באמצעות המתג שלו. הוא מציג גם את הפקודה ל-root של סעיף 2: יש להריץ אותה, מפני שאת הלוגים שנוצרו אחרי התקנת המודול (`/var/log/apache2`) ניתן לקרוא רק עם הרשאת הקריאה ש-root מעניק.
- אם משהו עדיין חסר, הדרישות מציגות אותו שוב.
- אם המודול כבר מופעל, הגדרה מחדש גם מגלה מחדש את המקורות שלו ומריצה את האבחון שלו.

מודול מופעל שמאבד מאוחר יותר את הדרישות שלו (מישהו מסיר את ModSecurity) נשאר מופעל: האבחון שלו ואזהרת התקינות «ModSecurity כבר אינו טעון» (סעיף 15) מדווחים על כך, וכיבוי שלו היה משתיק את האזהרה הזו עצמה. רכיב האיסוף בודק את הדרישות כשהוא מופעל וכשההגדרות שלו משתנות, לעולם לא באופן תקופתי; גם `manage.py modules` ו-`manage.py doctor` מציגים אותן (סעיף 17).

**כיבוי והפעלה של מודול Apache.** תחת **מודולים › מותקנים**, יש להשתמש במתג של «Apache + ModSecurity» ולאשר. כל עוד הוא כבוי, localSIEM אינו קורא את הלוגים של Apache, אינו מריץ את האבחון שלו או את הכללים שלו ואינו שולח ממנו התראות; עדיין ניתן לחפש את האירועים שכבר נשמרו. כדי לחדש, יש להפעיל שוב את המתג (אפשרי רק כל עוד Apache ו-ModSecurity קיימים): רכיב האיסוף ממשיך מהמיקום שבו עצר בכל לוג (תוך מעקב אחר הרוטציות שבוצעו בינתיים), כך שהוא קורא גם את מה ש-Apache כתב בזמן שהמודול היה כבוי ושולח את כל ההתראות הנדרשות.

**הגדרות מודול Apache** (מודולים › מותקנים › Apache + ModSecurity › הגדרה):

| הגדרה | שימוש |
|---|---|
| רק המקורות שלמטה | לא לגלות את הלוגים מתוך התצורה של Apache: לקרוא רק את המקורות שנוספו ידנית |
| מקורות שנוספו ידנית | לוגים לקריאה בנוסף לאלה שהתגלו (פרטים בהמשך) |
| קובץ התצורה של Apache | ריק: נמצא אוטומטית (`/etc/apache2/apache2.conf` ב-Debian, `/etc/apache2/httpd.conf` ב-Alpine). גם הגדרה מחדש מחפשת את Apache שם |
| מרווח הגילוי (שניות) | באיזו תדירות התצורה של Apache נקראת מחדש כדי למצוא vhosts ולוגים חדשים (ברירת המחדל 3600) |
| סף החסימה של ModSecurity | 0: נקרא מהתצורה של ה-CRS (`tx.inbound_anomaly_score_threshold`), או 5 אם הוא אינו מופיע שם |
| ימי למידה לקובצי PHP חדשים | במהלך הימים הראשונים, קובץ PHP שלא נראה קודם אינו מדווח כחדש (הכלל `apache-webshell`; ברירת המחדל 3) |

**הוספת לוג ידנית.** ב-**מקורות שנוספו ידנית**, יש ללחוץ על «הוספת מקור» ולמלא את **סוג** (access.log, error.log או לוג הביקורת של ModSecurity), **נתיב** (מוחלט) ובמקרה הצורך, **Vhost**, **LogFormat** (עבור לוג גישה בפורמט משלו), **סוג לוג הביקורת** (טורי או מקבילי) ו-**תיקיית האחסון של הביקורת** (עבור לוג ביקורת מקבילי). «הסרה» מוחקת מקור. יש ללחוץ על «שמירת ההגדרות»: רכיב האיסוף מגלה מחדש את המקורות מיד והלוג החדש מופיע ב-**מקורות**. אם הוא מוצג כבלתי קריא, יש להעניק ל-`localsiem` הרשאת קריאה לתיקייה שלו (סעיף 3.7).

**מהמודול `apache` אל `apache2`.** עד localSIEM 2.1 מודול Apache נקרא `apache`; כעת הוא `apache2` (התיקייה `mod-apache2/` במאגר, מותקן ב-`/opt/localsiem/modules/apache2/`, הדף `/admin/dashboard/modules/installed/apache2/`). בשרת שהיה בו `apache`, התקנת `apache2` משאירה את שניהם טעונים: הישן ממשיך להחזיק בלוגים של Apache (שניהם מוצאים את אותם מקורות), `apache2` אינו מציג מקורות עד שמסירים את התקנת הישן, וההגדרות של `apache` אינן עוברות מעצמן. להעברה:

1. יש לרשום את ההגדרות ששונו בדף של המודול `apache` (הגדרה): מקורות שנוספו ידנית, קובץ התצורה של Apache, מרווח הגילוי, סף החסימה, ימי הלמידה.
2. יש להתקין את `apache2` תחת מודולים › ניתנים להתקנה.
3. יש להסיר את התקנת המודול `apache`: **הסרת התקנה**, בשורה שלו תחת מודולים › מותקנים או בדף שלו. רכיב האיסוף מופעל מחדש, ומאותו רגע `apache2` קורא את הלוגים של Apache.
4. יש לפתוח את הדף של `apache2`, להזין שוב את ההגדרות האלה ולשמור אותן. (לחלופין, בתור root, ניתן להעתיק ב-`/opt/localsiem/config/settings.json`, בתוך `"modules"`, את מה שנמצא תחת `"apache"` אל `"apache2"`, ולאחר מכן להפעיל מחדש את localSIEM.)

הכללים שומרים על המזהים שלהם (`apache-bruteforce`…) ועל השינויים שלהם, וגם המיקומים שנקראו בכל לוג והזיכרון של אזהרות התקינות נשמרים: `apache2` ממשיך מהמקום שבו `apache` עצר, בלי לקרוא דבר פעמיים. האירועים שהמודול `apache` שמר נשארים זמינים לחיפוש (`module:apache`).

## 14. ניהול

הלשוניות האלה נמצאות רק בלוח הבקרה של מנהל המערכת:

- **מודולים** (סעיף 13), בשני חלקים: **מותקנים** (`/admin/dashboard/modules/installed/`), הרשימה עם המתג של כל מודול, **הגדרה** (דרישות והגדרה מחדש, הגדרות, מקורות, אבחון וכללים של המודול), **עדכון** (כשבמאגר יש גרסה חדשה יותר) ו-**הסרת התקנה**; ו-**ניתנים להתקנה** (`/admin/dashboard/modules/installable/`), המודולים של המאגר שעדיין אינם מותקנים, עם **דרישות** ו-**התקנה**. מודולים מותקנים, מתעדכנים ומוסרים רק שם.
- **משתמשים › חשבונות** (`/admin/dashboard/users/accounts/`): יצירת חשבונות (נוצרת סיסמה שמוצגת פעם אחת; יש לשנות אותה בהתחברות הראשונה), איפוס הסיסמה או האימות הדו-שלבי, הפעלה או השבתה, שינוי התפקיד, מחיקה. תמיד יש לפחות מנהל מערכת פעיל אחד.
- **משתמשים › טוקני גישה** (`/admin/dashboard/users/tokens/`): **יצירת טוקן** עבור חשבון אנליסט פעיל (מנהלי מערכת מתחברים תמיד עם הסיסמה שלהם, ועם הגורם השני כשהאימות הדו-שלבי פעיל), עם תווית אופציונלית ותוקף של 7, 30, 90 (ברירת מחדל), 180 או 365 ימים. כתובת ה-URL לגישה, `https://<server>:10443/auth/login/auto?token=...`, מוצגת **פעם אחת בלבד**, עם כפתור «העתקה»: יש למסור אותה לאנליסט (סעיף 6). הרשימה מציגה לכל טוקן את החשבון והתווית, את 4 התווים האחרונים שלו, את המצב שלו (פעיל, פג תוקף, מבוטל, או לא שמיש כשהחשבון מושבת או שאינו עוד אנליסט), מתי ועל ידי מי הוא נוצר, מתי יפוג תוקפו ואת השימוש האחרון בו (זמן ו-IP). **ביטול תוקף** עוצר אותו מיד; הסשנים שכבר נפתחו באמצעותו מסתיימים כשתוקפם פג. סשן שנפתח עם טוקן אינו מבקש לא גורם שני ולא שינוי סיסמה. ניסיונות כושלים נספרים לצורך הנעילה הזמנית של ההתחברות.
- **SOC**: כתובת URL, טוקן (לעולם אינו מוצג במלואו), קובץ CA אופציונלי, **בדיקת החיבור** (שולח אות חיים), מצב המסירה, אות החיים האחרון, השגיאה האחרונה, התור (ממתינות, נשלחו, נדחו) ו-**שליחת התור עכשיו**. בנוסף, כתובת ה-SIEM שיש למסור ל-SOC. ה-SOC הוא אופציונלי (סעיף 5).
- **ערוצים** (`/admin/dashboard/channels/`), בשני חלקים, **כללי** (נפתח כברירת מחדל) ו-**Telegram**: ההודעות ש-localSIEM שולח ישירות, מלבד ההתראות שהוא מוסר ל-SOC (בהמשך).
- **הגדרות**: שמירת נתונים, גודל מרבי בדיסק, כתובות IP מורשות (הכתובת שלך חייבת להופיע ברשימה), אימות דו-שלבי (כבוי כברירת מחדל; הפעלתו הופכת אותו לחובה לכל החשבונות ומנתקת מיד את החשבונות שעדיין לא הגדירו אותו, כולל החשבון שלך, והם מגדירים אותו בהתחברות הבאה שלהם; כיבויו שומר את אפליקציות האימות שכבר הוגדרו למקרה שיופעל שוב), מגבלת הזמן של חיפוש, מגבלת הייצוא, חלון הקיבוץ והחוצץ, חלון הקורלציה והחומרה מתחת לסף. השינויים חלים מיד. הכללים כבר אינם כאן: הם מוגדרים בכל מודול (מודולים › מותקנים › הגדרה).
- **ביקורת חיפושים**: מי חיפש מה ומתי.
- **התחברויות** (`/admin/dashboard/logins/`): כל התחברות ל-localSIEM וכל ניסיון כושל, החדשים ביותר קודם: זמן, חשבון, שיטה (סיסמה, סיסמה וגורם שני, או טוקן גישה), תוצאה (הצלחה או כישלון), הסיבה לכישלון (שם משתמש או סיסמה שגויים, קוד גורם שני שגוי, ננעל אחרי כמה כישלונות, ההתחברות ארכה זמן רב מדי, טוקן לא ידוע, שפג תוקפו או מבוטל, החשבון מושבת, החשבון אינו חשבון אנליסט), IP ודפדפן. ניתן לסנן לפי תוצאה; **טעינת עוד** טוען התחברויות ישנות יותר. הן נשמרות כל עוד ההתראות נשמרות (365 ימים כברירת מחדל).

המצב של רכיב האיסוף, של הדיסק ושל מסד הנתונים נמצא בסקירה הכללית (סעיף 8).

### ערוצים: הודעות ישירות (Telegram)

מלבד מסירת כל התראה ל-SOC, localSIEM יכול לשלוח את החשובות ביותר דרך **ערוץ**. בשלב זה הערוץ הוא **Telegram**.

**כללי** (`/admin/dashboard/channels/general/`):

- **שליחת הודעות דרך הערוצים**: מפעיל או מכבה את כל הערוצים בבת אחת.
- **חומרה מינימלית**: נשלחות ההתראות בחומרה זו ומעלה (ברירת המחדל: גבוהה).
- **שפת ההודעות**: כל אחת מ-15 השפות של ממשק האינטרנט (ברירת המחדל en-US). הכלל והתיאור של ההתראה נשארים כפי ש-localSIEM כתב אותם.
- טבלה עם כל ערוץ: המצב שלו (כבוי, לא מוגדר, פועל או שגיאה), ההודעות שנשלחו, ההודעה האחרונה והשגיאה האחרונה.

**Telegram** (`/admin/dashboard/channels/telegram/`):

1. ב-Telegram, יש לפתוח את **@BotFather**, לשלוח `/newbot` ולבצע את השלבים שלו. הוא נותן את **הטוקן של הבוט** (`123456789:AA...`; המספר שלפני הנקודתיים הוא המזהה של הבוט).
2. יש לפתוח את הצ'אט עם הבוט וללחוץ על **Start** (או להוסיף את הבוט לקבוצה שתקבל את ההודעות, או כמנהל של הערוץ שיקבל אותן): בוט אינו יכול לכתוב למי שלא פנה אליו קודם.
3. כדי למצוא את **מזהה הצ'אט**: יש לשלוח הודעה כלשהי לבוט ולפתוח בדפדפן את `https://api.telegram.org/bot<token>/getUpdates`; המזהה הוא המספר שאחרי `"chat":{"id":`. המזהה של קבוצה מתחיל ב-`-` וזה של ערוץ ב-`-100`; ערוץ או קבוצה ציבוריים ניתן לציין גם בתור `@username`.
4. יש לכתוב את הטוקן ואת מזהה הצ'אט, לסמן את **שליחת ההודעות דרך Telegram** וללחוץ על **שמירה ושליחת הודעת בדיקה**. אם Telegram מסרב לה, ההודעה מציינת מדוע (לדוגמה `Unauthorized`: טוקן שגוי; `Bad Request: chat not found`: מזהה צ'אט שגוי, או שאיש לא לחץ על Start).

הטוקן נשמר בשרת ב-`/opt/localsiem/config/telegram-bot-token` (הרשאות 600) ולעולם אינו מוצג במלואו; **הסרת הטוקן** מוחקת אותו ומכבה את Telegram. השרת צריך גישה אל `https://api.telegram.org` (פורט 443 יוצא).

כל הודעה מציינת את החומרה, הכלל, התיאור, המודול, מספר האירועים, ההופעה הראשונה והאחרונה (UTC) ואת החיפוש שמציג אותם. localSIEM שולח לכל היותר הודעה אחת בשנייה. אם Telegram אינו עונה, הוא מנסה שוב כמה פעמים; אם Telegram מסרב להודעה (טוקן שגוי, צ'אט לא ידוע, בוט חסום), הוא זונח אותה ומציג את השגיאה. ההודעות הממתינות אובדות אם localSIEM מופעל מחדש: הערוצים הם התרעה ישירה, וה-SOC עדיין מקבל כל התראה.

## 15. אזהרות תקינות ומה לעשות

גם אלה נשלחות ל-SOC (הכללים `localSIEM health: …`), בקיבוץ כדי שלא יחזרו על עצמן:

| אזהרה | חומרה | מה לעשות |
|---|---|---|
| לוג קוצץ, נעלם או הוחלף מחוץ לרוטציה | גבוהה | ייתכן שמישהו מוחק עקבות. יש לבדוק למי הייתה גישה לשרת באותו זמן, ואת הלוגים האחרים שלו. |
| ModSecurity כבר אינו טעון, או שהמנוע הועבר ל-Off | גבוהה | אם איש לא עשה זאת בכוונה, ההגנה הושבתה: יש לבדוק את התצורה של Apache ואת השינויים האחרונים בה. |
| מקור לוג אינו קריא | בינונית | בדרך כלל הרשאות אחרי רוטציה: יש להריץ שוב בתור root את הפקודה של סעיף 2 (`manage.py setup-modules`) או להעניק ל-`localsiem` הרשאת קריאה (סעיף 3.7). רק לוג ש-localSIEM יכול היה לקרוא קודם מעורר אותה: לוג שמעולם לא ניתן היה לקרוא (מודול שהותקן זה עתה, לפני הפקודה של סעיף 2) מופיע רק במצב המודול («שגיאה», לא ניתן לקרוא אחד המקורות). |
| מקור לוג שקט במשך זמן רב (24 שעות) | בינונית | יש לוודא ש-Apache עדיין כותב לקובץ הזה (שינויים ברישום, דיסק מלא). |
| חסרה ה-IP האמיתית של הלקוח | בינונית | כמעט כל הבקשות מגיעות מכתובת פרטית אחת: אתר האינטרנט נמצא מאחורי proxy ו-Apache רושם את ה-IP שלו, ולכן הכללים לפי IP אינם פועלים עבור הבקשות האלה. |
| שורות רבות לא נותחו (יותר מ-5%) | נמוכה | הפורמט של הלוג השתנה: בדף המודול (מודולים › מותקנים › הגדרה) יש ללחוץ על «גילוי מחדש והרצת האבחון», כדי שהמודול יקרא את הפורמט החדש; האבחון מתאר את הפורמט של כל לוג. |
| מעט שטח פנוי בדיסק, או ששמירת הנתונים קוצרה מחוסר מקום | בינונית | יש לפנות מקום או להגדיל את הגודל המרבי בדיסק. בינתיים localSIEM שומר פחות פרטים. |

<a id="retention"></a>
## 16. שמירת נתונים ודיסק

אירועים נשמרים 90 יום והתראות 365 יום. מסד הנתונים לעולם אינו גדל מעבר למקסימום שלו (ברירת המחדל: הקטן מבין 15% מהדיסק ו-10 GB): האירועים הישנים ביותר נמחקים ראשונים, באצוות קטנות, והשטח חוזר לדיסק. כשיש מעט שטח פנוי בדיסק, localSIEM מפסיק לשמור את הפרטים הכבדים (הכותרות והגופים של רשומות הביקורת); כשכמעט אין שטח, הוא שומר רק את האירועים שהם חלק מהתראה, ומזהיר את ה-SOC. ניתן לשנות את הערכים עם `--retention-days` ו-`--max-disk` (לדוגמה `--max-disk 5G`) או תחת ניהול › הגדרות.

<a id="cli"></a>
## 17. שורת הפקודה

בתור root, `/opt/localsiem/venv/bin/python /opt/localsiem/webapp/backend/manage.py`:

| פקודה | שימוש |
|---|---|
| `list-users` | החשבונות והאימות הדו-שלבי שלהם |
| `create-user NAME --role admin\|analyst --credentials /root/webapp-credentials.txt` | חשבון חדש עם סיסמה שנוצרה אוטומטית |
| `reset-password NAME --credentials /root/webapp-credentials.txt` | סיסמה חדשה (שיש לשנות בהתחברות הבאה) |
| `reset-mfa NAME` | האימות הדו-שלבי מוגדר מחדש בהתחברות הבאה |
| `doctor` (`--json`) | הדרישות והמקורות של כל מודול מופעל, ועבור מודול כבוי שיש לו דרישות, מה שהוא צריך לפני שניתן להפעיל אותו (יש להריץ אותה בתור `localsiem`, סעיף 4) |
| `modules` | המודולים המותקנים: שם, גרסה, מופעל, מושבת או לא נטען, תיקייה, ומתחת למודול הדרישות שחסרות לו בשרת; והמודולים שלא ניתן לטעון, עם הסיבה |
| `read-paths` | התיקיות שהמודולים המותקנים קוראים (`setup-modules` ותוכנית ההתקנה מעניקים ל-`localsiem` הרשאת קריאה אליהן) |
| `soc-test` | שולחת אות חיים ל-SOC |
| `setup-modules` | בתור root, הפקודה שממשק האינטרנט מציג אחרי התקנת מודול, אחרי עדכון שמשנה את הלוגים שהמודול קורא, ועם הגדרה מחדש: הרשאת קריאה ל-`localsiem` לתיקיות של המודולים המותקנים (ACL, גם לרוטציות הבאות; הקבוצה `adm` ב-Debian), הפעלה מחדש של localSIEM והאבחון בתור `localsiem`. עם `--no-restart` (מה שתוכנית ההתקנה משתמשת בו) היא רק מעניקה את הרשאת הקריאה. |

מודולים מותקנים, מתעדכנים ומוסרים רק מממשק האינטרנט (סעיף 13): אין לכך פקודה.

שירותים: localSIEM פועל כשני שירותים של משתמש המערכת `localsiem`, רכיב האיסוף (`localsiem`) וממשק האינטרנט (`localsiem-web`). `systemctl status localsiem localsiem-web` מציג אותם ו-`systemctl restart localsiem localsiem-web` מפעיל אותם מחדש (Debian), או `rc-service localsiem status; rc-service localsiem-web status` ו-`rc-service localsiem restart; rc-service localsiem-web restart` (Alpine); יש להפעיל מחדש את שניהם אחרי העתקה או מחיקה ידנית של מודול ב-`/opt/localsiem/modules/` (ממשק האינטרנט עושה זאת בעצמו כשהוא מתקין, מעדכן או מסיר מודול). לוגים: `journalctl -u localsiem -u localsiem-web` (Debian) או `/opt/localsiem/log/` (Alpine); בהפעלה, רכיב האיסוף רושם את השורה `Modules: ...` עם כל מודול, הגרסה שלו והאם הוא מופעל או כבוי, ואת `Module <name>: requirements missing: ...` עבור מודול שחסרות לו דרישות.
