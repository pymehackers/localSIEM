## 1. localSIEM の機能

localSIEM は、インストールされたサーバーのサービスを **モジュール**（サービスごとに1つ）で監視します。読み取るのはそのサーバーのログだけで、他のマシンからログを受け取ることはありません。**Apache + ModSecurity** モジュールは Apache の Web サイトを監視します。リクエストごとに、`access.log` の行、`error.log` の行、ModSecurity の監査ログの記録という3つの記録を、リクエストの `UNIQUE_ID` を使って結合します。すべて検索用に保存されます。そのうえで、localSIEM は SOC に送るべきものを判断します。

localSIEM は、保護対象と同じ Debian または Alpine のサーバー上で、その Web サイトと並んで、システムユーザー `localsiem` の2つのサービスとして動作します。localSIEM 自身の Web 画面はポート 10443 で待ち受けます。ポート 80 や 443 を使うことはなく、サーバーの Web サイトに手を加えることもありません。SOC（任意、第5章）のほかに、最も重要なアラートを **Telegram** で送信でき（第14章）、SOC のアナリストには **検索ツール**（検索フィールド1つと時間範囲）を提供します（第9章）。パスワード、Cookie、トークン、リクエスト本文がサーバーの外に出ることはありません。メモリ使用量は少なく（通常時は約 100 MB、ピーク時は約 200 MB）、ディスクを満杯にすることもありません（第16章）。

**SOC に送信されるのは、まだ誰も対処していないものだけです。**

| 状況 | SOC に送信されるか |
|---|---|
| ModSecurity がフェーズ 1–2 でリクエストをブロックした（アプリケーションが受け取る前） | **いいえ。** localSIEM に残って検索でき、その IP の次のアラートに件数として表示されます。 |
| ModSecurity がフェーズ 3–4 でレスポンスをブロックした（アプリケーションはすでにリクエストを実行していた） | はい |
| ModSecurity が `DetectionOnly`（何もブロックしない）の状態でのルール一致 | はい |
| ブロックしきい値未満のルール一致 | はい（重大度 `low`） |
| localSIEM のルールによるシグナル（ブルートフォース、Web シェル、機密ファイル、列挙、データベースエラー） | はい |
| ヘルスの問題と、痕跡削除の可能性 | はい |

**SOC に送信されるものの重大度**

| 状況 | 重大度 |
|---|---|
| ブロックされなかったルール一致、応答 3xx、4xx、5xx | 中 |
| ブロックされなかったルール一致、応答 2xx | 高 |
| フェーズ 3–4 でブロック | 高 |
| 成功の兆候：ブロックされなかったデータ漏えいまたは Web シェルのルール（950–955）、直後の SQL エラー、新しい `.php` への 2xx の POST | 重大 |
| ブロックしきい値未満（多くはアプリケーションの誤検知） | 低（設定で変更可能） |

**グループ化。** モジュール、vhost、IP、カテゴリ、重大度の組み合わせごとに、10分間のウィンドウで1件のアラートになります。重大なアラートはただちに送信され、それ以外は短時間に集中したイベントをまとめるために60秒待ってから、件数と共に送信されます。数千件のリクエストを送るスキャナーでも、生成されるアラートは数千件ではなく数件です。重大度が上がった場合（たとえば、同じ攻撃が今度は 200 応答を受けた場合）は、別のアラートになります。

**SOC に決して送信されないもの：** リクエストやレスポンスの本文、Cookie、`Authorization` ヘッダー、パスワード、トークン（マスクしたものも含む）、そしてフェーズ 1–2 ですでにブロックされたもの（件数としてのみ送信）。localSIEM は、何かを保存する前に、機密性のある値（`password`、`pass`、`pwd`、`passwd`、`token`、`secret`、`api_key`、`apikey`、`auth`、`session` と、ヘッダー `Authorization`、`Cookie`、`Set-Cookie`、`X-Api-Key`、`Proxy-Authorization`）を `***` でマスクします。

**モジュール。** localSIEM のコア（保存、検索、ルール、グループ化、SOC への配信、ヘルス）はすべてのサービスで共通で、各モジュールが1つのサービスに固有の部分を追加します。Apache + ModSecurity モジュール（`apache2`）は `localSIEM-modules` リポジトリ（GitHub）から提供され、インストール、更新、アンインストールは Web 画面からのみ行い、localSIEM のインストーラーで行うことはありません。このモジュールをインストールしても、Apache や ModSecurity がインストールされることはありません。どのモジュールも、同じように Web 画面からインストール、更新、アンインストールします。第13章では、モジュールのインストールと更新、状態の確認、有効化と無効化、構成の方法を説明します。

<a id="installation"></a>
## 2. インストール

インストールは2段階です。localSIEM のコアと、その後のモジュール（後述の手順 2）です。root として、GitHub から直接実行します：

```bash
# Debian 13
curl -fsSL -H 'Accept: application/vnd.github.raw+json' https://api.github.com/repos/PYMEHackers/localSIEM/contents/deploy/install-update-reinstall-debian.sh | bash -s -- --install --allow-from 203.0.113.10 --soc-token TOKEN
# Alpine 3.24（先に apk add bash curl を実行）
curl -fsSL -H 'Accept: application/vnd.github.raw+json' https://api.github.com/repos/PYMEHackers/localSIEM/contents/deploy/install-update-reinstall-alpine.sh | bash -s -- --install --allow-from 203.0.113.10 --soc-token TOKEN
```

localSIEM の Web 画面は常に **ポート 10443 の HTTPS** で待ち受けます。インストーラーはこのポートが空いていることを確認し、他のサービスが使っている場合は停止します。アクションとオプションは `bash -s --` の後に指定します。インストーラーは必要なもの（`venv` を含む Python 3.13、OpenSSL、CA 証明書、ACL ツール、logrotate、curl、tar）を確認し、不足しているものをインストールします。このようにパイプで実行すると、`https://github.com/PYMEHackers/localSIEM` のブランチ `main` をダウンロードします。プロジェクトのコピーから実行した場合（`bash deploy/install-update-reinstall-debian.sh --install`）は、そのコピーをインストールします。

**アクション。** インストーラーには常に1つのアクションが必要です。指定しない場合は停止し、アクションの一覧を表示します：

| アクション | 用途 |
|---|---|
| `--install` | localSIEM がないサーバーに localSIEM をインストールします。localSIEM のもの（`/opt/localsiem`、そのサービス、`localsiem` ユーザー。途中で失敗したインストールのものも含む）が見つかった場合は停止し、`--update` と `--reinstall` を案内します。 |
| `--update` | インストール済みの localSIEM を更新します。データ、アカウント、設定、モジュール、以前に指定したオプション（後述）は保持されます。 |
| `--reinstall [--yes]` | `--uninstall` と同じように（後述）インストール済みの localSIEM をすべてのデータと共に削除し、新しいパスワードでゼロから再インストールします。最初に `yes` の入力を求めます（`--yes` を付けると確認しません。端末がない場合に必要です）。新しいコピーのダウンロードとオプションの確認が終わるまで、何も削除しません。以前のインストールのオプションは保持されないため、もう一度指定してください。 |
| `--uninstall [--yes]` | localSIEM とそのすべてのデータをサーバーから削除します（後述）。単独で指定します。 |

`--update` と `--reinstall` は、localSIEM がインストールされていない場合は停止します。その場合は `--install` を使ってください。

`--install`、`--update`、`--reinstall` のオプション：

| オプション | 用途 |
|---|---|
| `--allow-from LIST` | Web 画面を開くことを許可する IP と CIDR（カンマ区切り）：SOC と管理者 |
| `--soc-url URL` | 既定値は `https://soc.pymehackers.com` |
| `--soc-token TOKEN` | SOC におけるこのクライアントの取り込みトークン。任意：SOC がなくても、localSIEM は単独で動作します（第5章） |
| `--soc-ca-file PATH` | プライベート証明書を使用する SOC（テストサーバー）の場合のみ |
| `--domain NAME` | 証明書と SIEM アドレスに使うサーバー名（既定値：ホスト名） |
| `--certificate PATH --private-key PATH` | 使用する証明書。指定しない場合、localSIEM は `--domain` の Let's Encrypt 証明書があればそれをコピーし（更新のたびに再コピーします）、なければ自己署名証明書を作成します。 |
| `--retention-days N`、`--max-disk SIZE` | 保持（第16章） |
| `--enable-mfa`、`--disable-mfa` | 2段階認証を有効（すべてのアカウントで必須）または無効にします。指定しない場合、新規インストールでは無効になり、更新では 管理 › 設定 で選択した状態が保持されます（第14章）。 |
| `--rotate-credentials` | 新しい JWT 署名シークレットを作成し、`/root/webapp-credentials.txt` に書き込みます |
| `--ref REF` | ダウンロードする localSIEM のブランチまたはタグ（既定値 `main`） |
| `--source-url URL` | GitHub のものの代わりにインストールする localSIEM のアーカイブ（`.tar.gz`）（ミラー） |
| `--modules-repository URL`、`--modules-ref REF` | Web 画面がモジュールのインストールと更新に使うリポジトリ（または `.tar.gz` アーカイブ）と、そのブランチまたはタグ（第13章）。既定値：`https://github.com/PYMEHackers/localSIEM-modules`、ブランチ `main`。 |

**常に最新バージョン。** GitHub は変更のたびに `raw.githubusercontent.com` のファイルを最大5分間キャッシュに保持するため、上記のコマンドはキャッシュのない GitHub API を通じてインストーラーを読み込みます。その後、インストーラーはその API にブランチがどのコミットを指しているかを問い合わせてそのコミットを正確にダウンロードし、経路上のすべてのサーバーに、キャッシュしたコピーで応答しないよう要求します。トークンがない場合、GitHub が許可する API リクエストは IP アドレスごとに1時間あたり60回です。拒否された場合、コマンドは `403` で失敗します（しばらく待ってから再実行してください）。インストーラーの問い合わせだけが失敗した場合、インストーラーは警告を出してブランチをダウンロードします。

オプションは `/opt/localsiem/config/install.env` に記憶されます。オプションなしの `--update` は、それらを保持します。更新するには：

```bash
# Debian 13（Alpine の場合：install-update-reinstall-alpine.sh）
curl -fsSL -H 'Accept: application/vnd.github.raw+json' https://api.github.com/repos/PYMEHackers/localSIEM/contents/deploy/install-update-reinstall-debian.sh | bash -s -- --update
```

インストーラーのログは `/root/webapp-install.log` で、インストーラーが作成するパスワードは `/root/webapp-credentials.txt` にあります（どちらもモード 600）。進行状況は番号付きの手順（`[3/12] Getting localSIEM`）で表示され、完了したものには `✓`、警告には `!`、失敗には `✗`、情報には `·` が付きます。端末ではカラーで表示されます（`NO_COLOR=1` または `LOCALSIEM_COLOR=never` で色を無効にできます）。apt-get または apk、curl、tar、pip の出力はログにのみ書き込まれ、いずれかが失敗すると、その最後の20行が画面に表示されます。ログには同じ行が色なしで、時刻は記録用の形式で書き込まれます。最後に、有効なすべてのモジュールの診断（第4章）を実行して概要を表示します。概要には、Web 画面のアドレス（SOC に伝える SIEM アドレスでもあります）、認証情報ファイル、ログ、SOC の状態が示され、その後に次の手順が続きます。失敗した場合は、どの手順で停止したかを示します。

**アンインストール。** `--uninstall` は localSIEM をサーバーから削除します。そのサービスを停止して削除し、`/opt/localsiem`（コード、設定、すべてのイベントとアラートを含むデータベース、証明書、モジュール）、`localsiem` ユーザー、`setup-modules` が付与したログの読み取り権限、Apache モジュールの旧バージョン（1.2.0 以前）の `--configure-apache` オプションが追加した Apache の設定（`localsiem.conf`。configtest と Apache のリロードを伴います）、logrotate のファイル、Let's Encrypt のフック、`/root/webapp-credentials.txt` の localSIEM のエントリ（ほかに何も残らない場合はファイルごと削除）を削除します。最初に `yes` の入力を求めます（`--yes` を付けると確認しません。端末がない場合に必要です）。サーバーに localSIEM のものが何も残っていない場合は、«Nothing of localSIEM was found on this server.» と表示します。インストーラーのログ、インストーラーが追加したパッケージ、`mod_unique_id`（Debian）、Apache のログは残ります。その設定ファイルによって Apache が書き込んでいた `localsiem_access.log` と `modsec_audit.log` も残ります。localSIEM が Apache のログを変更したり削除したりすることはありません。アンインストールするには：

```bash
# Debian 13（Alpine の場合：install-update-reinstall-alpine.sh）
curl -fsSL -H 'Accept: application/vnd.github.raw+json' https://api.github.com/repos/PYMEHackers/localSIEM/contents/deploy/install-update-reinstall-debian.sh | bash -s -- --uninstall
```

**再インストール。** 1回の手順でゼロからやり直すには、`--reinstall` を使います。同じようにすべてを削除し、localSIEM を再インストールします（オプションはもう一度指定してください）：

```bash
# Debian 13（Alpine の場合：install-update-reinstall-alpine.sh）
curl -fsSL -H 'Accept: application/vnd.github.raw+json' https://api.github.com/repos/PYMEHackers/localSIEM/contents/deploy/install-update-reinstall-debian.sh | bash -s -- --reinstall --allow-from 203.0.113.10 --soc-token TOKEN
```

**2. モジュール。** localSIEM のインストーラーは **モジュールを1つもインストールしません**。モジュールを使える状態に localSIEM を準備するだけで、更新ではインストール済みのモジュール（とそのログの読み取り権限）が保持されます。モジュールのインストールは **Web 画面からのみ** 行います。モジュール › インストール可能（第13章）には、`localSIEM-modules` リポジトリのモジュールのうち、まだインストールされていないものが一覧表示されます。このリポジトリには独自のインストーラーはありません。localSIEM はそこからモジュールをダウンロードし、そのフォルダー（リポジトリでは `mod-<name>/`）を `/opt/localsiem/modules/<name>/` にコピーして（`tests/` フォルダーはコピーされません。再インストールしたモジュールは以前の設定を取り戻します）、コレクターを再起動します。モジュールの更新とアンインストールも Web 画面から行います。リポジトリに新しいバージョンがある場合の **更新** と、**アンインストール** で、どちらも モジュール › インストール済み にあります（第13章）。

モジュールのログを読み取るには root 権限が必要なため、モジュールをインストールすると、サーバーで root として実行するコマンドが Web 画面のダイアログに表示されます：

```bash
/opt/localsiem/venv/bin/python /opt/localsiem/webapp/backend/manage.py setup-modules
```

このコマンドは、インストール済みの各モジュールが宣言するログフォルダー（Apache モジュールの場合は `/var/log/apache2`。第3章の項目 7 を参照）に対する読み取り権限を、今後のローテーションで作られるファイルも含めて `localsiem` ユーザーに付与し、localSIEM を再起動して、`localsiem` として診断を実行します。いつでも再実行できます。localSIEM が付与するこの読み取り権限が、root がモジュールのために行うことのすべてです。

**モジュールをインストールしても、それが監視するソフトウェアがインストールされることはなく**、それ以外のものもインストールされません。モジュールはサーバーにすでにあるもので動作し、`/opt/localsiem/` の外にあるものを変更することはありません。新しいモジュールは、作成者が決めたとおりに有効または無効の状態で起動します。ただし、サーバーに必要なもの（Apache モジュールの場合は Apache と ModSecurity 2）が不足している場合は **無効** の状態でインストールされ、Web 画面に不足しているものが表示されます。そのスイッチは、**再構成** でそれが検出されるまでロックされたままです（第13章）。モジュールの状態は **モジュール › インストール済み** に表示されます（第13章）。

<a id="requirements"></a>
## 3. Apache と ModSecurity の要件

これらは Apache + ModSecurity モジュールの要件です。Apache と ModSecurity 2 自体は、先にインストールしておく必要があります。これらがないと、モジュールを有効にできません（第13章）。localSIEM が Apache の設定を勝手に変更することはなく、Apache のログやその形式、書き込み方法を変更することもありません。モジュールは、サーバーがすでに書き込んでいるログを読み取り、それに合わせて動作します。モジュールの診断（第4章）は各要件を確認します。CRS と `SecRuleEngine` を含む ModSecurity（項目 1）、`mod_unique_id`（項目 2）、読み取り権限（項目 7）については、不足しているものごとに、適用すべき正確なスニペットまたはコマンドを示します。ログ（項目 3〜6）については説明するだけで、変更を提案することはありません。

1. **OWASP CRS を含む ModSecurity 2**（`SecRuleEngine On` または `DetectionOnly`）。どちらでも動作します。`DetectionOnly` では何もブロックされないため、すべての一致が SOC に送信されます。
2. **`mod_unique_id`**。ModSecurity 2 が動作するためにそもそも必要なもので（これがないと何も検査しません。Alpine では既定で読み込まれません）、各リクエストの3つの記録を結合します。
3. **アクセスログ**（Apache が書き込むままのもの）。どの形式でも動作します（`combined`、`vhost_combined`、`common`、または設定内の任意の `LogFormat`）。各行は、クライアント IP、メソッド、URI、ステータス、時刻によってリクエストと結合され（«弱い相関»）、vhost は `%v` から、それがない場合は監査記録の Host ヘッダーとポートから取得します。形式にミリ秒、`%v`、`%{UNIQUE_ID}e` も含まれている場合（一部のサーバーがすでに書き込んでいる `localsiem_combined` の行など）、各行は `UNIQUE_ID` によってリクエストと結合され、`%D` があれば localSIEM は所要時間も取得します。クライアント IP、時刻、リクエスト行、ステータスのいずれかが形式に欠けているアクセスログは、そのまま読み取られますが、その行をリクエストと結合することはできません。それらのリクエストは ModSecurity の監査ログで確認できます。形式にディレクティブが1つもない `CustomLog` は、すべての行に同じテキストを書き込むため、読み取られません。
4. **`mod_remoteip`**。ログにどの IP が記録されるかを決めます。Web サイトがプロキシやロードバランサーの背後にあり、Apache がこれを使っていない場合、ログにはプロキシの IP が記録され、アラートや IP ごとのルールも同様になります。診断とヘルス警告 «Real client IP missing»（第15章）がそのことを知らせます。
5. **ModSecurity の監査ログ**（ModSecurity が書き込むままのもの）：シリアルまたはコンカレント、JSON またはネイティブ、含まれるパートもそのままです。これがない場合（`SecAuditEngine Off` または `SecAuditLog` がない場合）、localSIEM は `error.log` だけで判断し、リクエストカードにはヘッダーやルールの一覧がありません。パート `H` がないと、実行されたアクションを読み取れません。パート `E`（レスポンス本文）は、記録されていても SOC に送信されることはありません。パート `K`（実行されたすべてのルールの全文）は保存されません。コンカレント形式（トランザクションごとに1ファイル）では、ModSecurity は通常モード 600 でファイルを作成するため、localSIEM がそれを読み取れるのは `localsiem` が読み取れる場合だけです（項目 7）。
6. **ソースでのマスク**：ModSecurity がディスク上の監査ログをマスクしない場合（`sanitise` アクション）、そのファイルにはパスワードや Cookie が含まれることがあります。localSIEM はそれらを保存前にマスクし、SOC に送信することはありません。
7. **`localsiem` ユーザーによるログの読み取り権限**。第2章の root 用コマンド（`manage.py setup-modules`）が、インストール済みのモジュールが宣言するフォルダー（Apache モジュールの場合は `/var/log/apache2`）に対してこれを行い、localSIEM のインストーラーも更新のたびに再度行います。Debian では `localsiem` を `adm` グループに追加し、Alpine と同様に ACL を使って `localsiem` にそれらのフォルダーの読み取り権限を与えます。今後のローテーションで作られるファイルも読み取れるよう、デフォルト ACL も設定します。別のフォルダーに手動で追加したログ（第13章）にも同じ権限が必要です。たとえば `setfacl -m g:localsiem:rx /srv/logs`、`setfacl -d -m g:localsiem:r /srv/logs`、`setfacl -m g:localsiem:r /srv/logs/*.log` を実行します。localSIEM はログを読み取るだけで、書き込んだり、ローテーション、切り詰め、移動、削除をしたりすることはありません。ログの追跡を開始するとき（初回起動時、モジュールのインストール後や有効化後、または root が読み取り権限を与えた時点）は、ログの末尾から読み始めます。ログにすでにあったものは履歴であり、アラートの対象になることはありません。後から作成された vhost のログだけは、先頭から読み取られます（5 MB 以下の場合）。

<a id="doctor"></a>
## 4. 診断

各モジュールには独自の診断があります。Apache モジュールの診断は、第3章のすべての要件を確認し、不足しているものごとに、それを修正するスニペットまたはコマンドを示します。ログ（形式、`mod_remoteip`、監査ログ、マスク）については説明するだけで変更を提案することはなく、見つかったソース（とパイプ出力のログなど、読み取れないもの）を一覧表示します。診断は、localSIEM のインストールのたびに、および第2章の root 用コマンドの最後に実行され、各モジュールのページ（**モジュール › インストール済み › 構成**、第13章。ボタン «再検出して診断を実行» があります）に表示されます。また、有効なすべてのモジュールについて、いつでも実行できます：

```bash
runuser -u localsiem -- /opt/localsiem/venv/bin/python /opt/localsiem/webapp/backend/manage.py doctor   # Debian
su -s /bin/sh localsiem -c "/opt/localsiem/venv/bin/python /opt/localsiem/webapp/backend/manage.py doctor"   # Alpine
```

`✓` は正常、`!` は制限付きで動作、`✗` は修正が必要、`·` は一部の状況でのみ該当することを示します（端末ではカラーで表示され、UTF-8 を書き込めない環境では `+`、`!`、`x`、`-` になります）。読み込めないモジュールは、最初に `✗ Module <name> not loaded: <reason>` として表示されます。無効になっているモジュールには診断がありません。要件がある場合（第13章）は、代わりにその要件が表示されるので、モジュールを有効にできるかどうかがわかります。

<a id="soc"></a>
## 5. SOC との接続

localSIEM を SOC に接続するかどうかは任意です。SOC がない場合（トークンがない、または **アラートを SOC に送信** が無効の場合）、localSIEM は単独で動作します。すべてのアラートを **アラート** タブに «未送信» として保持し、後から送信することはありません。後で SOC を設定しても同様で、それ以降は新しいアラートだけが SOC に送信されます。チャネル（Telegram）は、SOC の有無にかかわらず動作します。

SOC の管理者は次のことを行います：

1. クライアント用の取り込みトークンを作成し（表示されるのは一度だけです）、あなたに渡します。これを `--soc-token` または **管理 › SOC** で設定してください。
2. クライアントの **SIEM アドレス** として `https://<server>:<port of localSIEM>` を設定します（インストーラーと 管理 › SOC に表示されます）。アラートを担当するアナリストは、このリンクを使って調査に訪れます。
3. SOC の送信元 IP をあなたに伝えます。それらを許可する IP（`--allow-from` または 管理 › 設定）に追加し、**ファイアウォールでは、それらの IP と管理者に対してのみポートを開放してください**。

localSIEM は5分ごとに **ハートビート** を送信します。SOC が一定時間（既定では60分）アラートもハートビートも受信しない場合、SOC は自チームに警告します。アラートは永続キューで待機するため、ネットワークの切断や再起動で失われることはなく、再送しても SOC で重複することはありません。クライアントがアラート番号をすべて使い切ったと SOC が応答した場合、localSIEM は送信を停止してキューを保持し、そのことを 管理 › SOC に表示します。

各アラートには、固定のルール名、localSIEM の検索に貼り付ける正確なクエリを含む説明、詳細情報が含まれます。詳細情報は、vhost、クライアント IP、メソッド、URI（マスク済み）、応答、ユーザーエージェント、ModSecurity のデータ（エンジン、アクション、フェーズ、スコア、しきい値、ルール、一致したデータ）、グループ（件数、初回と最終の時刻、サンプルの `UNIQUE_ID`）、および IP の **コンテキスト**（過去1時間のリクエスト数とブロックされたリクエスト数、ブロックされたルール、初めて確認された時刻）です。

<a id="signin"></a>
## 6. サインインとアカウント

`https://<server>:10443/` を開きます。サインインページはフォームだけで、ロゴ、ユーザー名、パスワード、**続行**、その下に言語とテーマがあります。アカウントは管理者が作成し、一般公開の登録はありません。パスワードは8文字以上です。**2段階認証** は既定では無効です。管理者がこれを有効にすると（管理 › 設定、第14章）、すべてのアカウントで必須になります。次回のサインイン時に、認証アプリ（Google Authenticator、Microsoft Authenticator、Aegis、FreeOTP など。«PYMEHackers localSIEM» として表示されます）で QR コードをスキャンしてそのコードを入力すると、以後のサインインでは毎回アプリのコードが求められます。何度か試行に失敗すると、サインインは数分間ロックされます。

**トークンによる直接アクセス。** 管理者は、アナリストにアクセス URL（`https://<server>:10443/auth/login/auto?token=...`）を渡すことができます（ユーザー › アクセストークン、第14章）。許可されたアドレスからこれを開くと、パスワードも第2要素も使わずにただちにサインインし、ユーザーダッシュボードの概要が開きます。サイトの別のページを開くには、`&next=/user/dashboard/search/?q=...` を追加します。トークンが機能しない場合は、サインインページにその理由（不明、期限切れ、または取り消し済みのトークン、あるいはアカウントが無効か、もうアナリストではない）が表示されます。URL はパスワードと同じように管理してください。この URL を持っている人は、有効期限が切れるか取り消されるまで、そのアカウントでサインインできます。パスワードまたはトークンによるすべてのサインインと、失敗したすべての試行は記録されます（サインイン履歴、第14章）。

サインインすると、ダッシュボードの **概要** が表示されます（第7章）。検索へのリンク（たとえば SOC からのもの）は、必要に応じてサインインページを開いた後、**同じ検索をそのパラメーターと共に** 開きます。

ロール：**アナリスト**（ユーザーダッシュボードで作業します：概要、検索、ライブビュー、アラート、モジュールの状態、アカウント）と **管理者**（管理者ダッシュボードで作業します：同じ内容に加えて、モジュールの構成と管理）。言語（de-DE、en-GB、en-US、es-AR、es-ES、fr-FR、he-IL、hi-IN、it-IT、ja-JP、ko-KR、pt-BR、pt-PT、ru-RU、zh-CN）、テーマ（システム、ライト、ダーク）、UTC の時計は、ダッシュボードの各ページのタイトルバーにあります。サインインページでは **続行** の下にあり、このブラウザーで最後に選択したものが初期値になります（選択していない場合は、ブラウザーとシステムのもの）。**続行** を押したときに表示されている言語が、アカウントの言語になります。ダッシュボードは、変更するまで、どのブラウザーでもその言語を使います。時刻は常に UTC で、ネイティブ形式 `2026/10/29@13:59:59.723` で表示されます。localSIEM が書き込むファイル（エクスポート、`/root/webapp-credentials.txt`、インストーラーのログ）と SOC に送信するアラートには、記録用の形式 `2026-10-29@13-59-59.723` が使われます。これも UTC です。

<a id="dashboards"></a>
## 7. 2つのダッシュボード

ロールごとに専用のダッシュボードがあり、アドレスを見ればどちらにいるかがわかります。サイドバーには、上部にロゴ、タブ（グループごとに区切り線）、下部に **サインアウト** があります。

| | 管理者ダッシュボード | ユーザーダッシュボード |
|---|---|---|
| 対象 | 管理者 | アナリスト |
| アドレス | `/admin/dashboard/<tab>/` | `/user/dashboard/<tab>/` |
| タブ | 概要、検索、ライブ、アラート；モジュール（インストール済みとインストール可能）、ユーザー（アカウントとアクセストークン）、SOC、チャネル（全般と Telegram）、設定、検索監査、サインイン履歴；アカウント | 概要、検索、ライブ、アラート、モジュール（状態のみ）、アカウント |

各タブには固有のアドレスがあり（たとえば `/admin/dashboard/logins/`）、`/admin/dashboard/` または `/user/dashboard/` を開くと概要が開きます。タブ内のセクションにも固有のアドレスがあります。`/admin/dashboard/users/` は `/admin/dashboard/users/accounts/` を開き、アクセストークンは `/admin/dashboard/users/tokens/` にあります。`/admin/dashboard/modules/` は `/admin/dashboard/modules/installed/` を開き、インストール可能なモジュールは `/admin/dashboard/modules/installable/` にあります。もう一方のダッシュボードのアドレスを開くと、自分のダッシュボードの同じタブに移動します。`/user/dashboard/search/?q=...` へのリンク（SOC からの通常のリンク）を開いた管理者には、`/admin/dashboard/search/` で同じ検索が表示されます。管理用のタブを開いたアナリストには、ユーザーダッシュボードの概要が表示されます。

**アナリストに表示されるもの。** 調査に必要なものはすべて表示されます。概要、検索とそのリクエストカード、ライブビュー、アラート、各モジュールの状態（有効か無効か、動作しているかどうか、そのカウンター）です。モジュールの有効化や無効化、構成、診断やルールの表示はできず、ユーザー、アクセストークン、SOC への接続、設定、検索監査、サインインの記録の管理もできません。

<a id="overview"></a>
## 8. 概要

両方のダッシュボードの最初のタブです。15秒ごとに更新され、次の内容を表示します：

- **イベント（24時間）**：そのうちアラートが発生した件数も表示されます。**ブロック（24時間）**：ModSecurity がすでに対処したもの（保存され、アラートは出ません）。**アラート（24時間）**：SOC への送信待ちの件数も表示されます。**稼働中のモジュール**：有効なモジュールのうち «有効・動作中» のものの数（すべて動作していれば緑色）。
- **過去24時間のアクティビティ**：1時間あたりのイベント数。各バーの青い部分は、ModSecurity がブロックしたものです。時間帯をクリックすると、そのイベントの検索が開きます。
- **モジュールの状態**：各モジュールとその状態（第13章）、読み取っているもの。«モジュールを表示» でモジュールタブが開きます。
- **システム**：コレクターが稼働しているかどうか（とそのバージョン）、稼働開始時刻、SOC との接続の状態、最終ハートビート、SOC への送信待ちアラート、ディスク空き容量、最大値に対するデータベースのサイズ。
- **最新のアラート**：最新の6件（重大度、ルール、IP、件数、状態、最終時刻）。«すべてのアラートを表示» でアラートタブが開きます。

<a id="search"></a>
## 9. 検索

**検索** タブには、検索フィールド1つと時間範囲（過去15分間、1時間、24時間、7日間、30日間、またはネイティブ形式によるカスタム範囲）があります。

| 構文 | 意味 |
|---|---|
| `word` | 元の（マスク済みの）テキストの全文検索。URL デコードしたものも対象 |
| `"exact phrase"` | フレーズ |
| `field:value` | フィールドが値と等しい（テキストフィールドでは大文字と小文字を区別しない） |
| `field:*part*` | ワイルドカード |
| `status:>=500`、`status:400..499`、`status:4xx` | 数値フィールドの比較と範囲 |
| `a b` / `a AND b`、`a OR b`、`NOT a` / `-a`、`( )` | 演算子と括弧 |

| グループ | フィールド |
|---|---|
| ネットワーク | `ip`、`vhost`、`host` |
| リクエスト | `method`、`uri`、`path`、`query`、`status`、`bytes`、`duration`（マイクロ秒）、`ua`、`referer` |
| 発生元 | `uid`（UNIQUE_ID）、`module`、`source`（`access`/`error`/`audit`） |
| ModSecurity | `rule`（CRS の ID、または `localsiem:<rule>`）、`category`、`phase`、`score`、`engine`（`on`/`detection-only`） |
| アラート | `severity`、`action`（`blocked`/`none`）、`alert`（SOC コード）、`sent`（`yes`/`no`） |
| 品質 | `parse`（`ok`/`partial`/`unparsed`） |

例：

- `ip:203.0.113.7` — 1つの IP に関するすべての記録
- `rule:942100` — その CRS ルールに一致したリクエスト
- `status:200 action:none category:sqli` — ブロックされずに 200 を受けた SQL インジェクション
- `uri:*wp-login*`
- `"union select"`
- `uid:ZTx1kH8AAQEAAB2gTkAAAAAB` — 1件のリクエスト
- `alert:c00007a0001F` — 1件の SOC アラートのリクエスト
- `(category:sqli OR category:xss) sent:no -status:404`

カテゴリ：`sqli`、`xss`、`lfi`、`rfi`、`rce`、`php`、`java`、`fixation`、`generic`、`protocol`、`multipart`、`scanner`、`method`、`data-leakage`、`webshell`、および localSIEM のルールのカテゴリ：`bruteforce`、`enumeration`、`sensitive-file`、`db-error`、さらに `health-*`。

構文エラーは、誤りの位置と共にフィールドの下に表示されます。制限時間（5秒）を超える検索では、範囲を絞り込むよう求められます。

結果ページには次のものが表示されます：

- **ヒストグラム**（時間軸）。各バーの青い部分は、ModSecurity がブロックしたものです。バーの上をドラッグする（または1本をクリックする）と、範囲を絞り込めます。
- クエリの **集計**：リクエスト数の多い IP、リクエスト数の多いパス、HTTP コード、頻出ルール。値をクリックすると、クエリに追加されます。
- **結果テーブル**（時刻、ソース、IP、メソッド、URI、コード、アクション、ルール、アラート）。新しいものから順に表示され、«さらに読み込む» があります。
- CSV または JSON への **エクスポート**（マスク済みのデータ、最大 10 000 行、時刻は記録用の形式 `2026-10-29@13-59-59.723`）と **リンクをコピー**（絶対時刻）。リンクの形式は `/user/dashboard/search/?q=<query>&from=<native time>&to=<native time>` です（管理者がコピーした場合は `/admin/dashboard/search/...`）。どちらのダッシュボードのリンクも、両方のロールで機能します。

すべての検索とエクスポートは記録され（誰が、何を、いつ）、管理者が閲覧できます。ログには個人データが含まれるためです。

<a id="card"></a>
## 10. リクエストカードとピボット

行をクリックすると、リクエストのカードが開きます。時刻、vhost、クライアント IP、メソッド、URI、コード、サイズ、所要時間、ユーザーエージェント、`UNIQUE_ID`、相関、実行されたアクション、ModSecurity エンジン、フェーズ、スコアとしきい値、カテゴリ、重大度、アラートが表示され、さらに記録ごとに、解析された内容（一致したルールとそのメッセージとデータ、リクエストヘッダーとマスク済みの本文、レスポンスヘッダー、エラー行、元の行）が表示されます。各記録のモジュールは、自身が表示できるものを追加します（Apache モジュールは、監査記録からヘッダーと本文を再構築します）。

カード内の注記：ModSecurity の痕跡がない 403 は **疑わしい** ものとしてマークされます（ブロックとしてはカウントしません）。**弱い相関** は、アクセスログに `UNIQUE_ID` がないため、アクセスログの行がクライアント IP、メソッド、URI、ステータス、時刻によってリクエストと結合されたことを意味します。そのリクエストについて **データベースエラー** が記録された場合も注記されます。

ピボット：**この IP**（その IP のすべてのアクティビティ）、**±5分**（リクエスト前後のタイムライン）、**ルール …**（一致した各ルール）、**このカテゴリ**、**この UNIQUE_ID**。

<a id="live"></a>
## 11. ライブビュー

**ライブ** タブには、コレクターが新しいイベントを保存するとすぐに（5秒間の相関ウィンドウの後で）それが表示され、最新のものが上に来ます。フィルターには検索の構文を使います。**一時停止** で更新が止まり、再開すると最新のイベントから続行します。

<a id="alerts"></a>
## 12. アラート

**アラート** タブには、localSIEM が生成したアラートが一覧表示されます。表示される項目は、SOC コード、重大度、ルール、IP、vhost、件数、初回と最終の時刻、状態です：

| 状態 | 意味 |
|---|---|
| バッファ内 | 送信前に、短時間に集中したイベントをまとめています（60秒） |
| キュー内 | SOC を待っています（ネットワークの停止、SOC が応答しない） |
| 送信済み | SOC が受け付けました。そのコードが表示されます |
| 拒否 | SOC がそのアラートを拒否しました。キューの残りは続行されます。管理 › SOC から再度キューに入れることができます。 |
| 未送信 | SOC が設定されていなかったか、送信が無効でした。アラートは localSIEM に残り、後から送信されることはありません（SOC は任意です。第5章） |

行をクリックすると、説明、**アラートのリクエスト**（最大50件。検索と同様に古いものから順に表示され、1件をクリックすると、リクエスト、ヘッダー、ModSecurity のルール、元の行を含むリクエストカードが開きます）、ウィンドウ、`external_id`、SOC に送信したアラートそのものが表示されます。**検索** でグループの検索が開きます。アラートを開いている間、一覧は更新されません。

<a id="modules"></a>
## 13. モジュール

管理者ダッシュボードでは、**モジュール** タブに2つのセクションがあり、それぞれに固有のアドレスがあります。既定で開く **インストール済み**（`/admin/dashboard/modules/installed/`。`/admin/dashboard/modules/` はここに移動します）と、モジュールをインストールする **インストール可能**（`/admin/dashboard/modules/installable/`。後述）です。アナリストには、インストール済みモジュールの一覧だけが、セクションなしで表示されます（`/user/dashboard/modules/`）。

**インストール済み** には、インストール済みのモジュールが1行に1つずつ、全幅で、モジュールのページのヘッダーと同じレイアウトで一覧表示されます。上部に名前、ID、バージョンがあり、その下に **状態**、概要、その状態の理由、さらに有効な場合はカウンター（読み取り中のソース、過去1時間の行数、最終データ、過去24時間のイベント数とブロックされたリクエスト数、診断の結果）が表示されます。管理者には、名前の右側にスイッチ、行の下部にボタンも表示されます。ページは10秒ごとに更新されます。モジュールが1つもインストールされていない場合は «インストール可能タブからモジュールをインストールしてください。» と表示されます（アナリストには «インストールされているモジュールはありません。モジュールは、管理者が モジュール › インストール可能 でインストールします。»）。

| 状態 | 意味 |
|---|---|
| 有効・動作中 | 有効で、コレクターに読み込まれ、ソースを読み取っています。診断の警告は注記として一覧表示され、状態は変わりません。 |
| 有効（警告あり） | 有効ですが、ソースがない、まだ存在しないソースがある、またはコレクターの起動後にインストールされました（`localsiem` サービスを再起動してください）。 |
| エラー | 読み込めない（理由が表示されます）、診断がエラーを報告している、または読み取れないソースがあります（`localsiem` ユーザーの権限。第3章の項目 7）。 |
| 変更を適用中… | 有効化または無効化した直後で、コレクターが変更を適用しています（数秒）。 |
| 無効 | 無効になっています。localSIEM はそのログを読み取らず、アラートも送信しません。すでに保存されているものは残ります。理由が «このサーバーには必要なものが不足しています：…» の場合は、要件を満たさないままインストールされたため、まだ有効にできません（後述の **要件と再構成** を参照）。 |
| 不明 | コレクターが稼働していません（`localsiem` サービス）。何も読み取られていません。 |

**アナリスト** にはこの一覧だけが表示されます。**管理者** には、各行に次のものもあります：

- 各モジュールの **スイッチ**：モジュールを有効または無効にします。無効にするときは確認を求められます。変更は、何も再起動せずにただちに適用されます。モジュールに必要なものがサーバーに不足している間は、スイッチはロックされます（«無効：要件が不足しています»）。
- **構成**：モジュールのページ（`/admin/dashboard/modules/installed/<name>/`。旧アドレスの `/admin/dashboard/modules/<name>/` からもここに移動します）を開きます：
  - ヘッダー：状態、モジュールがインストールされているフォルダー、スイッチ、«インストール済みモジュールに戻る»（インストール済みに戻ります）、«再検出して診断を実行»。要件のあるモジュールでは、ボタン «再構成» もあり、モジュールが無効の間、または要件が不足している間は、その **要件** も表示されます（後述）。
  - **設定**：モジュール独自の設定のフォーム。«設定を保存» でただちに適用されます。
  - **ソース**：読み取っているログ（種類、パス、vhost、過去1時間の行数と未解析の行数、最終データ、状態）と、その下に、見つかったが読み取っていないログとその理由。
  - **診断**：要件のチェック。不足しているものごとに、それを修正するスニペットまたはコマンドと «コピー» ボタンが表示されます（ログについては説明するだけです）。
  - **ルール**：モジュールの各ルールとそのスイッチ（«有効»）、重大度、しきい値、ウィンドウ（しきい値とウィンドウは、しきい値ルールとシーケンスルールのみ）。«ルールを保存» でただちに適用されます。
- **更新**：`localSIEM-modules` リポジトリにモジュールの新しいバージョンがある場合に表示されます。インストール済みを開くたびに、localSIEM はリポジトリを確認します。その間は «リポジトリで新しいバージョンを確認しています…» と表示され、確認に失敗した場合は «リポジトリで新しいバージョンを確認できませんでした：<error>» と表示されますが、一覧は通常どおり機能します。アクセスのたびにリポジトリをダウンロードしないよう、ブラウザーはその応答を10分間再利用します。インストール可能にある «リポジトリを確認» は常にダウンロードし直し、モジュールのインストール、更新、アンインストールを行うと、保持していた応答は破棄されます。10秒ごとの更新でダウンロードされることはありません。新しいバージョンがあるモジュールの行には、«リポジトリにバージョン X があります（インストール済みは Y）。» という通知と **更新** ボタンが表示されます。そのバージョンに新しい localSIEM が必要な場合、通知にはボタンがなく、そのことが示されます：«リポジトリにバージョン X がありますが、localSIEM Z 以降が必要です。インストールするには、localSIEM を更新してください。» **更新** は確認を求めます（«モジュールを更新»）。localSIEM はリポジトリから新しいバージョンをダウンロードし、インストール済みのものと入れ替えて、コレクターを再起動します。設定は保持され、モジュールの有効／無効の状態も変わりません。実行中、ボタンには «更新中…» と表示され、終了するとメッセージ «<モジュール> をバージョン X に更新しました。» が表示されます。ほかに行うことがある場合にのみ、ダイアログ «<モジュール> を更新しました» が開きます。新しいバージョンが別のログを読み取る場合は root 用のコマンド（`manage.py setup-modules`、第2章。«コピー» 付き）が表示され、コレクターが応答しなかった場合は `localsiem` サービスの再起動を求められます。
- **アンインストール**：インストール済みの各モジュールの行（読み込めないモジュールも含む）とそのページにあります。確認すると、localSIEM は `/opt/localsiem/modules/<name>/` を削除し、そのモジュールなしでコレクターを再起動します。そのログの読み取りとアラートの送信は停止します。すでに保存されているイベントとアラートは引き続き検索でき、設定（とルールの変更）は `settings.json` に残るため、再びインストールすると元に戻ります。root が `localsiem` に与えたログの読み取り権限は取り消されません。そのフォルダーを読み取るモジュールがほかにない場合は、手動で削除できます。たとえば `setfacl -R -x g:localsiem /var/log/apache2` と `setfacl -d -x g:localsiem /var/log/apache2` を実行します。

**インストール可能**（管理者のみ）には、カード «インストール可能なモジュール» があります。`localSIEM-modules` リポジトリ（既定では `https://github.com/PYMEHackers/localSIEM-modules`、ブランチ `main`。インストーラーのオプション `--modules-repository` と `--modules-ref` で変更できます）のモジュールのうち、このサーバーにまだインストールされていないものです。«リポジトリを確認» でリポジトリをダウンロードし、それらのモジュールを一覧表示します。各モジュールには、名前、ID、バージョン、概要と、ボタンまたは注記が表示されます：

| ボタンまたは注記 | 意味 |
|---|---|
| 要件 | モジュールがサーバー上で必要とするものと、それをインストールするコマンドを表示します（後述） |
| インストール | モジュールをインストールします |
| localSIEM X 以降が必要 | インストールできません。先に localSIEM を更新してください |
| リポジトリのモジュールが無効です | インストールできません |

**要件** はダイアログ «<モジュール>：要件» を開きます。モジュール自身が宣言した（`module.json` の `install_requirements`）、モジュールがサーバー上で必要とするものと、それをインストールするコマンドが表示されます。モジュールをインストールしても、それが監視するソフトウェアがインストールされることはないため、これらのコマンドはモジュールをインストールする **前に** サーバーで実行してください。ダイアログには、このサーバーのシステム向けのコマンド（«このサーバー：Debian GNU/Linux 13 (trixie)»）が2回、それぞれ «コピー» 付きで表示されます。**root として** と **sudo を付けて**（同じコマンドの先頭に `sudo` を付けたもの）で、サーバーの端末に root として、または sudo を使用できるユーザーとして貼り付けられます。モジュールの注記が最初に表示されます（たとえば、Alpine には ModSecurity 2 のパッケージがないこと）。このサーバーのシステム向けのコマンドをモジュールが宣言していない場合、ダイアログには宣言されているすべてのシステム（Debian と Alpine）向けのコマンドが表示されます。何も宣言していない場合は «このモジュールは、サーバーにインストールするものを宣言していません。» と表示されます。localSIEM がこれらのコマンドを実行することはありません。

リポジトリのすべてのモジュールがすでにインストールされている場合は、そのことが表示されます（«リポジトリのモジュールはすべてインストール済みです。»）。インストール済みのモジュールがこの一覧に表示されることはありません。それらはインストール済みで更新します（前述の **更新**）。Web 画面でモジュールを再インストールしたり、古いバージョンをインストールしたりすることはできません。再インストールするには、モジュールをアンインストールしてから、ここで再びインストールしてください（設定は保持されます）。

この一覧が、モジュールをインストールする唯一の方法です。localSIEM はモジュールをダウンロードし、その `module.json` を検証して、そのフォルダー（リポジトリでは `mod-<name>/`）を `/opt/localsiem/modules/<name>/` にコピーし（`tests/` フォルダーは除きます。再インストールしたモジュールは以前の設定を取り戻します）、コレクターを再起動します。コレクターは数秒以内にモジュールを読み込みます。モジュールは一覧から消え、ダイアログ «<モジュール> をインストールしました» に次の手順が表示されます：

- `localsiem` がモジュールのログを読み取れるようにするには root 権限が必要なため、ダイアログには、サーバーで **root として実行するコマンド** が «コピー» ボタンと共に表示されます。`manage.py setup-modules`（第2章）で、読み取り権限を与えて localSIEM を再起動します。このコマンドを実行するまで、ログを読み取れないため、モジュールは «エラー» と表示されることがあります。
- 初回のインストール時に、モジュールに必要なものがサーバーに不足している場合、モジュールは無効の状態でインストールされます。ダイアログには、コマンドの代わりに不足しているものが一覧表示され、それが揃ったらインストール済みでモジュールを開き（**構成**）、**再構成** を押すよう案内されます（後述）。

ダイアログには2つのボタンがあります。«閉じる» と、インストール済みを開く «インストール済みモジュールを表示» です。この一覧と、インストール済みでの新しいバージョンの確認には、サーバーから GitHub（HTTPS）に接続できる必要があります。

**要件と再構成。** モジュールをインストールしても、それが監視するソフトウェアがインストールされることはありません。モジュールは、有効にする前にサーバーに必要なものを宣言できます。Apache モジュールには、Apache（その設定：`apache2.conf`、`httpd.conf`、または設定 **Apache の設定ファイル** で指定したファイル）と、読み込まれた ModSecurity 2（`mod_security2`。ModSecurity 3 は対象外）が必要です。初回のインストール時にこれらが不足している場合、モジュールは **無効** の状態でインストールされ（«無効»、理由は «このサーバーには必要なものが不足しています：…»）、そのスイッチは **ロック** されます。モジュールのページには、無効の間も、診断と同じように要件（タイトル、詳細、不足しているものをインストールするコマンドと «コピー»）が一覧表示されます。不足しているものをインストールしたら（Apache が標準以外の場所にある場合は、**Apache の設定ファイル** を設定して設定を保存してから）、**再構成** を押してください。localSIEM は保存された設定で、もう一度それを探します。

- すべて揃っている場合、スイッチのロックは解除されますが、モジュールは有効になりません。スイッチで有効にしてください。第2章の root 用コマンドも表示されます。モジュールのインストール後に作成されたログ（`/var/log/apache2`）は、root が与える読み取り権限がないと読み取れないため、このコマンドを実行してください。
- まだ不足しているものがある場合は、要件に再び表示されます。
- モジュールがすでに有効な場合、再構成はソースの再検出と診断の実行も行います。

有効なモジュールが後から要件を満たさなくなった場合（誰かが ModSecurity をアンインストールした場合など）も、モジュールは有効のままです。診断とヘルス警告 «ModSecurity is no longer loaded»（第15章）がそれを報告します。モジュールを無効にすると、まさにその警告が出なくなってしまいます。コレクターは、起動時と設定の変更時に要件を確認し、定期的に確認することはありません。`manage.py modules` と `manage.py doctor` でも要件を確認できます（第17章）。

**Apache モジュールの無効化と有効化。** **モジュール › インストール済み** で «Apache + ModSecurity» のスイッチを操作し、確認します。無効の間、localSIEM は Apache のログを読み取らず、その診断もルールも実行せず、そこからアラートを送信することもありません。すでに保存されているイベントは引き続き検索できます。再開するには、スイッチを再び有効にします（Apache と ModSecurity がある場合のみ可能）。コレクターは各ログで停止した位置から続行する（その間に行われたローテーションも追跡します）ため、モジュールが無効だった間に Apache が書き込んだものも読み取り、必要なアラートを送信します。

**Apache モジュールの設定**（モジュール › インストール済み › Apache + ModSecurity › 構成）：

| 設定 | 用途 |
|---|---|
| 以下のソースのみ | Apache の設定からログを検出せず、手動で追加したソースのみを読み取ります |
| 手動で追加したソース | 検出されたログに加えて読み取るログ（後述） |
| Apache の設定ファイル | 空の場合は自動で検出します（Debian では `/etc/apache2/apache2.conf`、Alpine では `/etc/apache2/httpd.conf`）。再構成でも、ここで Apache を探します |
| 検出間隔（秒） | 新しい vhost やログを見つけるために、Apache の設定を読み直す間隔（既定値 3600） |
| ModSecurity のブロックしきい値 | 0：CRS の設定（`tx.inbound_anomaly_score_threshold`）から読み取り、見つからない場合は 5 |
| 新しい PHP ファイルの学習日数 | 最初の数日間は、初めて見る PHP ファイルを新規として報告しません（ルール `apache-webshell`。既定値 3） |

**ログを手動で追加する。** **手動で追加したソース** で «ソースを追加» を押し、**種類**（access.log、error.log、または ModSecurity の監査ログ）、**パス**（絶対パス）、必要に応じて **Vhost**、**LogFormat**（独自の形式のアクセスログの場合）、**監査ログの種類**（シリアルまたはコンカレント）、**監査ログの保存フォルダー**（コンカレントの監査ログの場合）を入力します。«削除» でソースを削除します。«設定を保存» を押すと、コレクターはただちにソースを再検出し、新しいログが **ソース** に表示されます。読み取れないと表示された場合は、そのフォルダーの読み取り権限を `localsiem` に与えてください（第3章の項目 7）。

**`apache` モジュールから `apache2` へ。** localSIEM 2.1 までは、Apache モジュールの名前は `apache` でしたが、現在は `apache2` です（リポジトリのフォルダーは `mod-apache2/`、インストール先は `/opt/localsiem/modules/apache2/`、ページは `/admin/dashboard/modules/installed/apache2/`）。`apache` があったサーバーに `apache2` をインストールすると、両方が読み込まれたままになります。古い方が Apache のログを保持し（どちらも同じソースを見つけるため）、古い方がアンインストールされるまで `apache2` にはソースが表示されません。また、`apache` の設定は自動的には移行されません。移行するには：

1. モジュール `apache` のページ（構成）で変更した設定を書き留めます：手動で追加したソース、Apache の設定ファイル、検出間隔、ブロックしきい値、学習日数。
2. モジュール › インストール可能 で `apache2` をインストールします。
3. モジュール `apache` をアンインストールします：モジュール › インストール済み のその行、またはそのページにある **アンインストール** を使います。コレクターが再起動し、それ以降は `apache2` が Apache のログを読み取ります。
4. `apache2` のページを開き、それらの設定を再度入力して保存します。（代わりに、root として `/opt/localsiem/config/settings.json` の `"modules"` 内で、`"apache"` の下にあるものを `"apache2"` にコピーしてから、localSIEM を再起動することもできます。）

ルールはその ID（`apache-bruteforce`…）と変更内容を保持し、各ログで読み取った位置とヘルス警告の記憶も保持されます。`apache2` は `apache` が停止したところから続行し、何も二重に読み取ることはありません。モジュール `apache` が保存したイベントは、引き続き検索できます（`module:apache`）。

## 14. 管理

これらのタブは、管理者ダッシュボードにのみあります：

- **モジュール**（第13章）。2つのセクションがあります。**インストール済み**（`/admin/dashboard/modules/installed/`）には、各モジュールのスイッチ、**構成**（要件と再構成、モジュールの設定、ソース、診断、ルール）、**更新**（リポジトリに新しいバージョンがある場合）、**アンインストール** を含む一覧があります。**インストール可能**（`/admin/dashboard/modules/installable/`）には、リポジトリのモジュールのうちまだインストールされていないものが、**要件** と **インストール** と共に表示されます。モジュールのインストール、更新、アンインストールは、ここでのみ行います。
- **ユーザー › アカウント**（`/admin/dashboard/users/accounts/`）：アカウントの作成（パスワードが生成されて一度だけ表示されます。初回のサインイン時に変更する必要があります）、パスワードまたは2段階認証のリセット、有効化または無効化、ロールの変更、削除。有効な管理者は常に1人以上存在します。
- **ユーザー › アクセストークン**（`/admin/dashboard/users/tokens/`）：有効なアナリストアカウントに対して **トークンを作成** します（管理者は常にパスワードで、2段階認証が有効な場合は第2要素も使ってサインインします）。ラベルは任意で、有効期間は 7、30、90（既定値）、180、365 日です。アクセス URL（`https://<server>:10443/auth/login/auto?token=...`）は «コピー» ボタンと共に **一度だけ** 表示されるので、アナリストに渡してください（第6章）。一覧には、各トークンのアカウントとラベル、最後の4文字、状態（有効、期限切れ、取り消し済み、またはアカウントが無効か、もうアナリストではない場合は使用不可）、作成日時と作成者、有効期限、最終使用（時刻と IP）が表示されます。**取り消し** でトークンはただちに使えなくなります。このトークンですでに開かれたセッションは、有効期限が切れた時点で終了します。トークンで開いたセッションでは、第2要素もパスワードの変更も求められません。失敗した試行は、サインインの一時的なロックの対象として数えられます。
- **SOC**：URL、トークン（全体が表示されることはありません）、任意の CA ファイル、**接続をテスト**（ハートビートを送信します）、配信の状態、最終ハートビート、最後のエラー、キュー（送信待ち、送信済み、拒否）、**今すぐキューを送信**。SOC に伝える SIEM アドレスもあります。SOC は任意です（第5章）。
- **チャネル**（`/admin/dashboard/channels/`）。2つのセクション、**全般**（既定で開きます）と **Telegram** があります。SOC に配信するアラートとは別に、localSIEM があなたに送信するメッセージです（後述）。
- **設定**：保持、最大ディスク使用量、許可する IP（自分のアドレスが一覧に含まれている必要があります）、2段階認証（既定では無効。有効にすると、すべてのアカウントで必須になり、まだ設定していないアカウントは、あなたのアカウントも含めてただちにサインアウトされ、次回のサインイン時に設定します。無効にしても、設定済みの認証アプリは、再び有効にしたときのために保持されます）、検索の制限時間、エクスポートの上限、グループ化のウィンドウとバッファ、相関ウィンドウ、しきい値未満の重大度。変更はただちに適用されます。ルールはここにはもうありません。各モジュールで構成します（モジュール › インストール済み › 構成）。
- **検索監査**：誰が、いつ、何を検索したか。
- **サインイン履歴**（`/admin/dashboard/logins/`）：localSIEM へのすべてのサインインと失敗したすべての試行が、新しいものから順に表示されます。時刻、アカウント、方式（パスワード、パスワードと第2要素、またはアクセストークン）、結果（成功または失敗）、失敗の理由（ユーザー名またはパスワードが正しくない、第2要素のコードが正しくない、複数回の失敗によりロック、サインインに時間がかかりすぎた、不明、期限切れ、または取り消し済みのトークン、アカウントが無効、アナリストアカウントではない）、IP、ブラウザー。結果で絞り込めます。**さらに読み込む** で古いものを読み込みます。アラートと同じ期間（既定では365日）保持されます。

コレクター、ディスク、データベースの状態は、概要にあります（第8章）。

### チャネル：あなたへのメッセージ（Telegram）

localSIEM は、すべてのアラートを SOC に配信するほか、最も重要なアラートを **チャネル** 経由であなたに送信できます。現在のチャネルは **Telegram** です。

**全般**（`/admin/dashboard/channels/general/`）：

- **チャネル経由でメッセージを送信**：すべてのチャネルを一度に有効または無効にします。
- **最小重大度**：この重大度以上のアラートが送信されます（既定値：高）。
- **メッセージの言語**：Web 画面の15言語のいずれか（既定値 en-US）。アラートのルールと説明は、localSIEM が記述したままになります。
- 各チャネルの表：状態（無効、未設定、動作中、またはエラー）、送信済みメッセージ、最終送信日時、最後のエラー。

**Telegram**（`/admin/dashboard/channels/telegram/`）：

1. Telegram で **@BotFather** を開き、`/newbot` を送信して、その手順に従います。**ボットのトークン**（`123456789:AA...`。コロンの前の数字がボットの ID です）が渡されます。
2. ボットとのチャットを開き、**開始** を押します（または、メッセージを受信するグループにボットを追加するか、チャンネルの管理者としてボットを追加します）。ボットは、先に話しかけてきていない相手にはメッセージを送れません。
3. **チャット ID** を調べます。ボットに任意のメッセージを送信し、ブラウザーで `https://api.telegram.org/bot<token>/getUpdates` を開きます。ID は `"chat":{"id":` の後にある数字です。グループの ID は `-` で始まり、チャンネルの ID は `-100` で始まります。公開チャンネルやグループは `@username` で指定することもできます。
4. トークンとチャット ID を入力し、**Telegram でメッセージを送信** にチェックを入れて、**保存してテストメッセージを送信** を押します。Telegram が拒否した場合は、通知にその理由が表示されます（たとえば `Unauthorized`：トークンが正しくない。`Bad Request: chat not found`：チャット ID が正しくないか、誰も開始を押していない）。

トークンはサーバー上の `/opt/localsiem/config/telegram-bot-token`（モード 600）に保存され、全体が表示されることはありません。**トークンを削除** でトークンを削除し、Telegram を無効にします。サーバーから `https://api.telegram.org`（アウトバウンドのポート 443）に接続できる必要があります。

各メッセージには、重大度、ルール、説明、モジュール、イベント数、初回と最終の時刻（UTC）、それらを表示する検索が含まれます。localSIEM が送信するメッセージは、最大で1秒に1件です。Telegram が応答しない場合は数回再試行し、Telegram がメッセージを拒否した場合（トークンが正しくない、不明なチャット、ボットがブロックされている）は、そのメッセージを破棄してエラーを表示します。localSIEM が再起動すると、送信待ちのメッセージは失われます。チャネルはあなたへの通知であり、SOC には引き続きすべてのアラートが届きます。

<a id="health"></a>
## 15. ヘルス警告と対処方法

これらも SOC に送信されます（ルール `localSIEM health: …`）。繰り返されないようにグループ化されます：

| 警告 | 重大度 | 対処方法 |
|---|---|---|
| ローテーション以外でのログの切り詰め、消失、置き換え | 高 | 誰かが痕跡を削除している可能性があります。その時刻にサーバーにアクセスできた人と、サーバーのほかのログを確認してください。 |
| ModSecurity が読み込まれなくなった、またはエンジンが Off になった | 高 | 誰も意図的に行っていない場合、保護が無効にされています。Apache の設定とその最近の変更を確認してください。 |
| ログソースを読み取れない | 中 | 通常はローテーション後の権限の問題です。root として第2章のコマンド（`manage.py setup-modules`）を再実行するか、`localsiem` に読み取り権限を与えてください（第3章の項目 7）。この警告が出るのは、localSIEM が以前は読み取れていたログだけです。一度も読み取れなかったログ（第2章のコマンドを実行する前の、インストールしたばかりのモジュールのものなど）は、モジュールの状態にのみ表示されます（«エラー»、読み取れないソースがあります）。 |
| ログソースが長時間（24時間）沈黙している | 中 | Apache がまだそのファイルに書き込んでいるかを確認してください（ログ設定の変更、ディスクの満杯）。 |
| Real client IP missing（実際のクライアント IP がない） | 中 | ほぼすべてのリクエストが1つのプライベートアドレスから来ています。Web サイトがプロキシの背後にあり、Apache がプロキシの IP を記録しているため、それらのリクエストには IP ごとのルールが機能しません。 |
| 解析されない行が多い（5% 超） | 低 | ログの形式が変わりました。モジュールのページ（モジュール › インストール済み › 構成）で «再検出して診断を実行» を押すと、モジュールが新しい形式を読み取ります。診断は各ログの形式を説明します。 |
| ディスクの空き容量が少ない、または容量不足のために保持期間が短縮された | 中 | 空き容量を確保するか、最大ディスク使用量を引き上げてください。その間、localSIEM が保存する詳細は少なくなります。 |

<a id="retention"></a>
## 16. 保持とディスク

イベントは90日間、アラートは365日間保持されます。データベースが最大サイズ（既定値：ディスクの 15% と 10 GB のうち小さい方）を超えることはありません。古いイベントから順に少しずつ削除され、その領域はディスクに戻されます。ディスクの空き容量が少なくなると、localSIEM は容量の大きい詳細データ（監査記録のヘッダーと本文）の保存を停止し、ほとんどなくなると、アラートに関係するイベントのみを保存して SOC に警告します。値は `--retention-days` と `--max-disk`（たとえば `--max-disk 5G`）で、または 管理 › 設定 で変更できます。

<a id="cli"></a>
## 17. コマンドライン

root として、`/opt/localsiem/venv/bin/python /opt/localsiem/webapp/backend/manage.py`：

| コマンド | 用途 |
|---|---|
| `list-users` | アカウントとその2段階認証 |
| `create-user NAME --role admin\|analyst --credentials /root/webapp-credentials.txt` | 生成されたパスワードで新しいアカウントを作成 |
| `reset-password NAME --credentials /root/webapp-credentials.txt` | 新しいパスワード（次回のサインイン時に変更） |
| `reset-mfa NAME` | 次回のサインイン時に2段階認証を設定し直す |
| `doctor`（`--json`） | 有効なすべてのモジュールの要件とソース、および要件のある無効なモジュールについては、有効にする前に必要なもの（`localsiem` として実行します。第4章） |
| `modules` | インストール済みのモジュール：名前、バージョン、有効・無効・未読み込みの別、フォルダー、モジュールの下にはサーバーに不足している要件。さらに、読み込めないモジュールとその理由 |
| `read-paths` | インストール済みのモジュールが読み取るフォルダー（`setup-modules` とインストーラーが `localsiem` にその読み取り権限を与えます） |
| `soc-test` | SOC にハートビートを送信 |
| `setup-modules` | root として実行する、モジュールのインストール後、モジュールが読み取るログが変わる更新の後、および再構成で Web 画面に表示されるコマンド：インストール済みモジュールのフォルダーに対する `localsiem` の読み取り権限（ACL。今後のローテーションも対象。Debian では `adm` グループ）、localSIEM の再起動、`localsiem` としての診断。`--no-restart`（インストーラーが使用）を付けると、読み取り権限を与えるだけです。 |

モジュールのインストール、更新、アンインストールは Web 画面からのみ行います（第13章）。そのためのコマンドはありません。

サービス：localSIEM は、システムユーザー `localsiem` の2つのサービス、コレクター（`localsiem`）と Web 画面（`localsiem-web`）として動作します。`systemctl status localsiem localsiem-web` で状態を表示し、`systemctl restart localsiem localsiem-web` で再起動します（Debian）。Alpine では `rc-service localsiem status; rc-service localsiem-web status` と `rc-service localsiem restart; rc-service localsiem-web restart` を使います。`/opt/localsiem/modules/` でモジュールを手動でコピーまたは削除した後は、両方を再起動してください（Web 画面でモジュールをインストール、更新、アンインストールした場合は、Web 画面が自動的に行います）。ログ：`journalctl -u localsiem -u localsiem-web`（Debian）または `/opt/localsiem/log/`（Alpine）。起動時に、コレクターは各モジュールとそのバージョン、有効か無効かを示す行 `Modules: ...` と、要件が不足しているモジュールについて `Module <name>: requirements missing: ...` をログに記録します。

**サーバー上のファイル**

| パス | 内容 |
|---|---|
| `/opt/localsiem/webapp/` | コアのコード |
| `/opt/localsiem/modules/` | インストール済みのモジュール（1つにつき1フォルダー、`apache2/`）。Web 画面が `localSIEM-modules` からインストールします |
| `/opt/localsiem/venv/` | Python の依存関係（システムのものとは別） |
| `/opt/localsiem/config/` | 設定、インストーラーのオプション（`install.env`）、SOC のトークン、シークレット（モード 600） |
| `/opt/localsiem/db/` | データベース |
| `/opt/localsiem/certificates/` | Web 画面の証明書 |
| `/opt/localsiem/log/`、`/opt/localsiem/run/` | ログ（Alpine）と実行時ファイル |
| `/root/webapp-install.log`、`/root/webapp-credentials.txt` | インストーラーのログと、インストーラーが作成したパスワード（モード 600） |
